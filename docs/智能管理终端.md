# 智能管理终端（AI 调用平台能力）

> 目标：让 LLM（本地 OpenWebUI / 外部 API）像人类一样调用平台能力，
> 完成「读知识库 → 整理 → 写回」这类跨模块任务。
> 本文档记录议题的探索结论、沙箱边界与实施顺序，避免重复踩坑。

## 一、P0 实测结论：tools 透传（已完成）

**日期**：2026-10（本会话）。
**被测端点**：LM Studio（`http://127.0.0.1:1234/v1`，OpenAI 兼容，本机已运行）。
**被测模型**：`qwen3-1.7b`、`qwen3.5-9b`。

### 结论

| 测试项 | 结果 |
|---|---|
| `tools` 字段透传 | ✅ 端点接受，无报错 |
| 模型生成 `tool_calls` | ✅ `qwen3.5-9b` 正确生成（`finish_reason: "tool_calls"`）；❌ `qwen3-1.7b` 不支持（`tool_calls: []`） |
| `tool` 角色消息回传 | ✅ 模型正确消费工具结果并生成最终回答 |
| 完整 tool loop | ✅ 一次调用工具 + 一次总结，全链路通 |

### 关键前提（否则模型「解释工具」而非「调用工具」）

1. **模型必须有 tool calling 能力**：`qwen3-1.7b` 不行，`qwen3.5-9b` 行。选错模型 = 静默失败。
2. **需要 `tool_choice: "auto"` + system prompt 明确「必须用工具」**：
   实测中，若只是 `tools` 数组 + 普通提问，模型会把工具定义读出来「讲解」，
   而不是生成 `tool_calls`。加了 `tool_choice: "auto"` 和引导语后才正确调用。
3. **`tool_calls` 是标准 OpenAI 格式**：与现有 `client.ts` 完全兼容，
   只需给 `聊天()` 加 `tools`/`tool_choice` 透传字段即可。

### 待验证（下一轮）

  直连 provider 已证实可行，OpenWebUI 大概率同样可行（它也走 OpenAI 兼容）。

### 补测结论（OpenWebUI，8090）

**日期**：2026-10（同会话）。
**被测端点**：OpenWebUI `http://127.0.0.1:8090/api/chat/completions`（`LMSTUDIO.*` 连接）。

| 测试项 | 结果 |
|---|---|
| `tools` 字段透传 | ✅ 完全工作 |
| `qwen3-1.7b`（直连时不支持）通过 OpenWebUI 生成 tool_calls | ✅ **意外成功**——OpenWebUI 对工具调用做了增强 |
| 完整 tool loop（回传 tool 结果） | ✅ 工作 |
| 中文内容 | ✅ 工作（但 curl 在 Windows 发中文会损坏 body，需用 Node/fetch） |

**关键发现**：
1. **OpenWebUI 不是纯透传**：它让原本不支持 tool calling 的 `qwen3-1.7b`
   也能生成 `tool_calls`（直连 LM Studio 时此模型返回空 `tool_calls`）。
   OpenWebUI 内部对工具调用做了 prompt 模板/中间层增强。
2. **Windows curl 发中文损坏 body**：`-d` 传中文会把 JSON 按 GBK 编码，
   OpenWebUI 报「parsing the body」。自动化测试必须用 Node/fetch。
3. **模型名含 `/` 也会触发「parsing the body」**：
   `LMSTUDIO.qwen/qwen3.5-9b`（斜杠）失败，`LMSTUDIO.qwen3-1.7b`（无斜杠）成功。
   这是 OpenWebUI 的已知限制，选模型时避开含斜杠的 id。

## 二、当前 AI 模块状态

- `ai.chat` 已支持 `tools`/`tool_choice` 透传（P1a）：
  - `client.ts` / `openwebui.ts` 的聊天参数有 `tools` 字段，
    解析模型返回的 `tool_calls` 为结构化结果；
  - `ai.chat` handler 支持 tools 参数，返回 tool_calls/finish_reason。
- `ai` 模块仍是**网关**（模型目录 + 统一入口）；工具循环在新 `agent` 模块（P2）。

## 三、沙箱边界（用户已确认的硬约束）

1. **AI 只能写 AI 标记的 Markdown 内容**：存储在 DB 的新节点类型 `aigc`，
   **绝不直接写磁盘文件**（`aigc_contents` 表持有内容）。
2. **AI 读访问是 opt-in**：默认全关闭；用户显式标记 `tags.ai_public` 的内容才可读。
3. **AI 不能运行自己的代码**：只能像人类一样调用平台插件/能力；
   **没有自定义脚本解释器**。允许「序列化批量调用序列」（数据，非代码）。
4. **权限边界用节点 `type`，不是 tag**：`aigc` 是 `nodes.type` 的 CHECK 枚举，
   tag 是用户可编辑数据，不能当权限边界。
5. **AI 有专属 `mkg.ai.*` 能力族**，按 `agent_id` 隔离——AI 只能改自己 session 的 `aigc` 节点。

## 五、关键设计决策（已定）

- **`ai` 模块继续做网关；新 `agent` 模块拥有工具循环**：关注点分离。
- **无 kugua 脚本解释器**：粗粒度能力 + 序列化批量调用序列（数据，不是代码）；
  先观察 AI 真实使用模式，再决定是否加原语。
- **能力返回必须语义完整**：说明「可读什么 / 为什么空 / 建议下一步动作」，
  绝不返回裸的「拒绝执行」。
- **mkg 重构先于 AI**：操作层/载体层/磁盘一致性/capability 声明先稳定（已完成第一阶段）。

## 六、依赖的 mkg 能力清单（已就绪）

mkg 模块已完成第一阶段重构，为 AI 提供了稳定的操作层：

- **载体判定**：`外部文件` vs `库内`（`判定载体` 单一真相源）
- **磁盘一致性**：`mkg.file.write` 写盘前 sha256 校验（防覆盖外部改动）
- **能力声明 88 条**：只读 37 / 写入 36 / 破坏 15，破坏类永不 MCP 暴露
- **关系层**：节点维度 `addRelation`/`getRelations`（`node_relations`）
- **读接口**：`mkg.data.read` 统一按 node/resource/path 读索引文本
