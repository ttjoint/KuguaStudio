# 智能管理终端（AI 调用平台能力）

> 目标：让 LLM（本地 OpenWebUI / 外部 API）像人类一样调用平台能力，
> 完成「读知识库 → 整理 → 写回」这类跨模块任务。
> 本文档记录议题的探索结论、沙箱边界与实施顺序，避免重复踩坑。

## 一、P0 实测结论：tools 透传（已完成）

**日期**：2026-10（本会话）。
**被测端点**：LM Studio（`http://127.0.0.1:1234/v1`，OpenAI 兼容，本机已运行）。
**被测模型**：`qwen3-1.7b`、`qwen3.5-9b`。

### 结论

| 测试项 | 结果 |
|---|---|
| `tools` 字段透传 | ✅ 端点接受，无报错 |
| 模型生成 `tool_calls` | ✅ `qwen3.5-9b` 正确生成（`finish_reason: "tool_calls"`）；❌ `qwen3-1.7b` 不支持（`tool_calls: []`） |
| `tool` 角色消息回传 | ✅ 模型正确消费工具结果并生成最终回答 |
| 完整 tool loop | ✅ 一次调用工具 + 一次总结，全链路通 |

### 关键前提（否则模型「解释工具」而非「调用工具」）

1. **模型必须有 tool calling 能力**：`qwen3-1.7b` 不行，`qwen3.5-9b` 行。选错模型 = 静默失败。
2. **需要 `tool_choice: "auto"` + system prompt 明确「必须用工具」**：
   实测中，若只是 `tools` 数组 + 普通提问，模型会把工具定义读出来「讲解」，
   而不是生成 `tool_calls`。加了 `tool_choice: "auto"` 和引导语后才正确调用。
3. **`tool_calls` 是标准 OpenAI 格式**：与现有 `client.ts` 完全兼容，
   只需给 `聊天()` 加 `tools`/`tool_choice` 透传字段即可。

### 待验证（下一轮）

- OpenWebUI（`8090`）的 `tools` 透传（当前未运行，需启动或换环境测）；
  直连 provider 已证实可行，OpenWebUI 大概率同样可行（它也走 OpenAI 兼容）。
- `gemma-4` / `qwen3.6-27b` 的 tool calling 能力（更大模型理论上更强）。

### 补测结论（OpenWebUI，8090）

**日期**：2026-10（同会话）。
**被测端点**：OpenWebUI `http://127.0.0.1:8090/api/chat/completions`（`LMSTUDIO.*` 连接）。

| 测试项 | 结果 |
|---|---|
| `tools` 字段透传 | ✅ 完全工作 |
| `qwen3-1.7b`（直连时不支持）通过 OpenWebUI 生成 tool_calls | ✅ **意外成功**——OpenWebUI 对工具调用做了增强 |
| 完整 tool loop（回传 tool 结果） | ✅ 工作 |
| 中文内容 | ✅ 工作（但 curl 在 Windows 发中文会损坏 body，需用 Node/fetch） |

**关键发现**：
1. **OpenWebUI 不是纯透传**：它让原本不支持 tool calling 的 `qwen3-1.7b`
   也能生成 `tool_calls`（直连 LM Studio 时此模型返回空 `tool_calls`）。
   OpenWebUI 内部对工具调用做了 prompt 模板/中间层增强。
2. **Windows curl 发中文损坏 body**：`-d` 传中文会把 JSON 按 GBK 编码，
   OpenWebUI 报「parsing the body」。自动化测试必须用 Node/fetch。
3. **模型名含 `/` 也会触发「parsing the body」**：
   `LMSTUDIO.qwen/qwen3.5-9b`（斜杠）失败，`LMSTUDIO.qwen3-1.7b`（无斜杠）成功。
   这是 OpenWebUI 的已知限制，选模型时避开含斜杠的 id。

## 二、当前 AI 模块状态

- `ai.chat` 已支持 `tools`/`tool_choice` 透传（P1a）：
  - `client.ts` / `openwebui.ts` 的聊天参数有 `tools` 字段，
    解析模型返回的 `tool_calls` 为结构化结果；
  - `ai.chat` handler 支持 tools 参数，返回 tool_calls/finish_reason。
- `ai` 模块仍是**网关**（模型目录 + 统一入口）；工具循环在新 `agent` 模块（P2）。

## 三、沙箱边界（用户已确认的硬约束）

1. **AI 只能写 AI 标记的 Markdown 内容**：存储在 DB 的新节点类型 `aigc`，
   **绝不直接写磁盘文件**（`aigc_contents` 表持有内容）。
2. **AI 读访问是 opt-in**：默认全关闭；用户显式标记 `tags.ai_public` 的内容才可读。
3. **AI 不能运行自己的代码**：只能像人类一样调用平台插件/能力；
   **没有自定义脚本解释器**。允许「序列化批量调用序列」（数据，非代码）。
4. **权限边界用节点 `type`，不是 tag**：`aigc` 是 `nodes.type` 的 CHECK 枚举，
   tag 是用户可编辑数据，不能当权限边界。
5. **AI 有专属 `mkg.ai.*` 能力族**，按 `agent_id` 隔离——AI 只能改自己 session 的 `aigc` 节点。

## 五、关键设计决策（已定）

- **`ai` 模块继续做网关；新 `agent` 模块拥有工具循环**：关注点分离。
- **无 kugua 脚本解释器**：粗粒度能力 + 序列化批量调用序列（数据，不是代码）；
  先观察 AI 真实使用模式，再决定是否加原语。
- **能力返回必须语义完整**：说明「可读什么 / 为什么空 / 建议下一步动作」，
  绝不返回裸的「拒绝执行」。
- **mkg 重构先于 AI**：操作层/载体层/磁盘一致性/capability 声明先稳定（已完成第一阶段）。

## 六、依赖的 mkg 能力清单（已就绪）

mkg 模块已完成第一阶段重构，为 AI 提供了稳定的操作层：

- **载体判定**：`外部文件` vs `库内`（`判定载体` 单一真相源）
- **磁盘一致性**：`mkg.file.write` 写盘前 sha256 校验（防覆盖外部改动）
- **能力声明 88 条**：只读 37 / 写入 36 / 破坏 15，破坏类永不 MCP 暴露
- **关系层**：节点维度 `addRelation`/`getRelations`（`node_relations`）
- **读接口**：`mkg.data.read` 统一按 node/resource/path 读索引文本

### 实测中发现的坑（环境层面）

`better-sqlite3` + Node 24 在 **数据库连接与 `fetch`/undici 同时存在时，进程退出阶段会偶发原生断言崩溃**
（`env != nullptr`，约 1/3 概率）。已确认与业务代码无关（纯 DB 脚本、纯 LLM 脚本各自稳定）。
规避方式：实测用例放 vitest 内跑（vitest 的 worker 生命周期不受影响）；
另在 `mkg.test.ts` 中避免 `WHERE col = ? ORDER BY pk` 的索引扫描组合。

## 八、权限定位：君子协议而非安全防护

**结论：本系统的权限控制是「防止自动化行为越界」的开发期约束，不是安全机制。**

### 为什么不做完整 RBAC

| 前提 | 推论 |
|---|---|
| 单机单用户，用户即超级管理员 | 角色继承、策略存储无意义 |
| 无互联网访问 | 不存在外部攻击面 |
| 所有模块同信任域（同进程） | 恶意代码可直接改 SQLite 文件，应用层拦不住 |

任何「防攻击」性质的权限设计在当前威胁模型下都是**假的**。

### 真正生效的约束：`危险` 闸门

`能力注册表.调用()` 加了执行层拦截：

```ts
if (声明.危险 && 调用者 !== "用户") {
  throw new Error(`能力 ${名称} 被标记为危险，不允许「${调用者}」调用`);
}
```

- **身份由主控按连接名判定**（不信任调用方自报）：`发送者 === "webui"` → `"用户"`，其余（模块/AI/定时）→ 程序
- 为什么不能自报：若让调用方传 `调用者` 参数，AI 入口多传一个字段就绕过了
- 覆盖范围：mkg 15 条破坏类 + job/mcp 的 `exec` 能力

**它防的不是攻击，是遗忘**——防止新写的模块/AI 入口「顺手」调了删除能力而没人发现。

### `权限` 字段的定位

`权限?: 权限[]`（`filesystem:read/write`、`exec` 等）是**描述性元数据**，不参与执行层校验。已在源码加注释说明，避免被误当安全机制依赖。

- 保留理由：帮助理解「这个能力碰了哪类资源」
- `校验权限()` 函数保留但标注「未接入调用链」，为将来真需要（如沙箱化插件）留锚点

### 调用路径的实际情况

- **UI 删除操作**：WebUI 直连模块（`request("mkg", "mkg.tag.delete")`），**不经** `capability.call` → 不受闸门限制（用户本来就是超级管理员）
- **AI / 模块调用**：走 `capability.call` → 受闸门约束

### 回归护栏

`packages/capability/test/danger-gate.test.ts`（7 用例）：
- 用户调用危险能力 → 放行
- 模块 / 默认 system / `capability.call` 调用 → 拒绝，且**断言未真正路由出去**
- 非危险能力 → 任何调用者放行
- 错误信息含能力名、标题、调用者、如何放行

反向验证：把闸门条件改为 `if (false && ...)` → 4 个用例红。

## 十、流式输出（本地模型体验的关键）

**问题**：本地 9B 模型单次回答可能 30-40 秒，工具循环 4-8 轮更久。非流式下用户只看到空白。

**实测数据**（`qwen/qwen3.5-9b`，极简问题）：
| 阶段 | 时间 |
|---|---|
| 思考首块 | **873ms** |
| 正文首块 | 37.7s |
| 完成 | 37.9s |

结论：**流式把「38 秒空白」变成「1 秒内有反馈」**。

### 实现

1. **`client.ts` 新增 `流式聊天()`**：SSE 逐行解析 `data:`，支持外部取消信号，坏块跳过不中断
2. **`ai.chat` 加 `流式` / `流式ID` 参数**：每块 `sendEvent("ai.chunk", ...)`
3. **WebUI server 转发** `ai.chunk` / `agent.progress` 事件到浏览器
4. **前端 `与AI对话`**：先落空回应 → 逐块填充 → 完成时用最终结果兜底
5. **`onBus` 支持取消订阅**：原来只 push 不移除，流式每次对话会累积监听器（内存泄漏）

### 踩到的真实坑

**推理模型的 `reasoning_content`**：`qwen3.5-9b` 是推理模型，流式增量先走 `delta.reasoning_content`（思考），正文 `delta.content` 后才出现。

- 最初只解析 `content` → 收到 0 块，以为是 SSE 解析错了
- 修正：`onReasoning` 单独回调，思考内容**不计入 reply**
- 前端：思考阶段显示「（正在思考…）」，不把思考当回答

**思考耗尽 token 预算**：`maxTokens: 300` 时，300 token 全被思考用光，`finish_reason: length` 且正文为空。

- 不能静默返回空串（前端显示空白，用户以为坏了）
- 修正：明确报错「模型把 token 都用在思考上，请调大 maxTokens（建议 ≥ 2000）」

**onError 重复通知**：内层主动 `onError` 后，外层 catch 又调一次 → 前端收到两条相同报错。用 `已通知` 标记去重。

### 回归护栏

`client.test.ts` 新增 11 用例：
- SSE 逐块解析 / 累计值增长 / 请求体 `stream:true`
- 空 delta 与非 data 行不崩溃 / 坏 JSON 块跳过
- 全空响应报错 / HTTP 错误触发 onError
- `reasoning_content` 不混入 reply / 思考耗尽预算明确报错 / 思考与正文交替各自累计

反向验证：把增量处理改成 `if (false && ...)` → 6 用例红。

### agent 工具循环进度

`agent.run` 新增 `进度ID` 参数，推送 `agent.progress` 事件：
`准备` → `思考(轮次)` → `决定调用(工具列表)` → `执行工具` → `工具完成` → `结束`

前端在任务气泡下方实时追加进度行（保留最近 6 条），用户能看到「现在在调什么工具」。
