# 仪表盘小组件（Widget）设计

> 状态：**设计稿，未实现**
>
> 目标：让插件/模块能把一个小块内容（CPU 曲线、内存环、下载速度数字）**注入主界面**，
> 而不是只能各占一个顶栏标签页。
>
> 依赖：`架构设计.md` 6.5（自带 UI 页）、6.6（声明式配置）、7（苦音协议）

---

## 一、问题

现在插件展示内容的唯一途径是 6.5 的**自带 UI 页**：声明 `"ui": { "entry": "ui/index.html" }`，
WebUI 就给它生成一个**顶栏标签页**，内容塞在 iframe 里。

这套机制适合「打开一个完整功能页」，但用来做「常驻小卡片」有三个硬伤：

1. **占位置**。装 5 个监控插件，顶栏就多 5 个标签。顶栏是导航，不是仪表盘。
2. **看不见**。标签页不激活时 iframe 根本不加载内容（`14-plugin-ui.ts` 里
   `激活时` 才设置 `src`），也就没有「实时显示」可言——用户得先点进去才知道 CPU 多高。
3. **重**。一个"显示下载速度"的卡片，为了它写一整个 HTML 页面，接入成本远高于收益。

所以需要**第二套表面**：小组件。

---

## 二、设计原则

### 2.1 小组件不是缩小的网页

这是最容易走偏的地方。直觉方案是「让插件写一个小 HTML，主界面用 iframe 摆进去」，
但会立刻遇到：

- N 个 iframe = N 个独立 JS 上下文 + N 份 CSS，内存和启动开销随插件数线性涨
- iframe 之间尺寸协商靠 postMessage 往返，第一次渲染必然跳一下
- 插件能做任意 DOM 操作 → 能盖住主界面、能劫持点击、能读不该读的东西

**结论：小组件的内容用数据结构描述，不用 HTML 描述。**
插件只上报「我要显示一个什么」，主界面用自己的组件库渲染。
这条和 6.6 的声明式配置页是同一个思路的延伸：

| 需求 | 方案 | 表达能力 |
|---|---|---|
| 开关、地址、下拉 | 声明式表单（6.6） | 低 |
| 实时数值、曲线、进度 | **小组件（本文）** | 中 |
| 音色试听、模型下载 | iframe 自定义页（6.5） | 高 |

三层按表达力递增，按需选用。常见需求落在前两层，就永远不用碰 iframe。

### 2.2 数据是推的，不是拉的

CPU 占用要每 2 秒刷一次。如果做成「主界面定时调插件」，那么：
主界面得知道插件支持轮询、轮询间隔多少、失败怎么办——这些本来该由插件自己决定。

正确方向是**插件主动推**：插件在自己的采样循环里，采到值就广播一次。
主界面只是被动更新显示。这也符合 2.1：主界面不需要理解「CPU」这个概念。

### 2.3 声明与数据分离

- **声明**（有什么组件、什么类型、放哪）：启动时上报一次，静态
- **数据**（当前值）：高频推送，可丢

分开的理由：声明要走「身份门禁」（6.3）审核，数据不需要；声明变了要重启生效，
数据每分钟变几百次。混在一起会导致高频数据被低频的门禁逻辑拖累。

## 三、形态：三种组件

先只做三种，覆盖绝大多数监控类需求，也不至于让渲染层变成半成品的前端框架。

### 3.1 `number` —— 单个数字

```
┌─────────────────┐
│ 下载            │
│ 12.4 MB/s       │  ← 大号数字
│ 总计 3.2 GB     │  ← 可选副标题
└─────────────────┘
```

```json
{ "id": "net.down", "类型": "number", "标题": "下载",
  "单位": "MB/s", "小数位": 1 }
```

推送：`{ "id": "net.down", "值": 12.4, "副标题": "总计 3.2 GB" }`

### 3.2 `gauge` —— 环形或条形占比

```
┌─────────────────┐
│   ◕ 68%         │  ← 环 + 百分比
│   内存          │
└─────────────────┘
```

```json
{ "id": "mem", "类型": "gauge", "标题": "内存",
  "最大": 100, "单位": "%", "外观": "ring" }
```

`外观`：`ring`（环）/ `bar`（横条）。超阈值变色由主界面统一处理（`警示` / `危险` 阈值可选）。

### 3.3 `sparkline` —— 时间序列小曲线

```
┌─────────────────┐
│ CPU  34%        │
│  ╱╲    ╱╲╱      │  ← 最近 N 个点
└─────────────────┘
```

```json
{ "id": "cpu", "类型": "sparkline", "标题": "CPU",
  "最大": 100, "单位": "%", "点数": 60 }
```

数据是**追加**而非覆盖：推送 `{ "id": "cpu", "值": 34.2 }`，主界面自己维护最近 `点数` 个值。
插件不需要每次推一整条数组，省带宽也省得插件自己维护环形缓冲。

> 为什么不做 `table` / `list` / `chart`：
> 表格看进程列表、多轴折线图这类需求真实存在，但它们更适合 iframe 页。
> 小组件的定位是「扫一眼就知道」，不是「展开研究」。

## 四、放在哪：槽位

主界面提供几个具名区域，插件声明自己想进哪个。

| 槽位 | 位置 | 适合 |
|---|---|---|
| `chat.top` | 聊天页顶部，横向一排 | 系统监控（CPU/内存/网速） |
| `chat.side` | 聊天页右侧栏，纵向堆叠 | 待办、日程、今日统计 |
| `statusbar` | 底部状态栏，极窄的一条 | 单行摘要（连接数、队列长度） |

**默认全部进 `statusbar`。** 理由是：不请自来的大块内容很烦。
插件要占更显眼的位置，得在声明里写明槽位，也就意味着它明确表达了意图。

**冲突处理**：同一槽位里按 `顺序`（数字，小的在前）排列，同序按插件名字典序。
不提供拖拽排序——那需要把布局状态持久化到配置里，属于以后的事。

## 五、协议

### 5.1 声明

插件在 `kugua-plugin.json` 里加一个字段（模块则在握手时的 `界面` 旁边加 `小组件`）：

```json
{
  "name": "sysmon",
  "ui": { "title": "系统监控", "entry": "ui/index.html" },
  "widgets": [
    { "id": "cpu",  "type": "sparkline", "title": "CPU",
      "unit": "%", "max": 100, "points": 60,
      "slot": "chat.top", "order": 10 },
    { "id": "mem",  "type": "gauge", "title": "内存",
      "unit": "%", "max": 100, "appearance": "ring",
      "slot": "chat.top", "order": 20 },
    { "id": "net.down", "type": "number", "title": "下载",
      "unit": "MB/s", "decimals": 1,
      "slot": "chat.top", "order": 30 }
  ]
}
```

> 清单文件里**用英文键**（`type`/`title`/`slot`），因为 `kugua-plugin.json` 是对外的、
> 会被第三方照着写；而运行时握手载荷继续用中文键，那是内部协议。
> 这和「SDK 公开 API 纯英文」是同一条约束。

### 5.2 数据推送

插件用现成的广播能力推，不新增通道：

```ts
ctx.broadcast("widget.data", { id: "cpu", value: 34.2 });
```

模块在苦音总线上：

```ts
客户端.broadcast("widget.data", { 来源: "sysmon", id: "cpu", 值: 34.2 });
```

主界面通过 `window.kugua.onBus` 收到后分发给对应组件。

**为什么要带 `来源`**：`id` 只在插件内部唯一（`cpu` 这个名字谁都想用），
全局唯一键是 `来源 + id`。主控收到广播时统一补上 `来源`，插件自己不许填
（否则可以冒充别的插件的数据）。

### 5.3 限流

高频推送是必然的（有人会每 100ms 推一次）。两条限制：

- **单插件每秒最多 20 次** `widget.data`，超出丢弃并计数
- 丢弃计数在插件管理页显示，让插件作者自己发现写错了

丢弃而不排队：旧数据没有价值，排队只会让显示越来越滞后。

## 六、安全边界

小组件比 iframe 页容易守，因为它不执行插件代码。但仍有三处要防：

| 风险 | 处理 |
|---|---|
| 插件上报恶意 HTML 当标题 | 标题/副标题一律 `textContent`，**绝不 innerHTML** |
| `id` 里塞奇怪字符 | 只允许 `[a-z0-9._-]`，其余拒绝该声明 |
| 声明数量爆炸 | 单插件最多 12 个小组件，超出截断并记日志 |
| 冒充其他插件推数据 | 主控强制覆盖 `来源` 字段 |
| 跨站请求伪造广播 | 广播走 `/api/broadcast`，已有同源检查 |

**不做的**：不搞沙箱隔离。小组件不放 iframe 正是为了性能，
而它不执行插件代码这个前提让隔离失去意义。

## 七、渲染实现要点

### 7.1 惰性挂载，但**不**惰性订阅

和 iframe 页不同，小组件在页面加载后**全部**挂载（哪怕用户当前在知识库页）。
原因：数据推送是需要有人接的，如果切回聊天页才订阅，那切过去的瞬间是空白，
用户得等第一次推送——体验上就是「卡一下」。

代价是所有小组件始终在更新 DOM。对 10 个以内的组件，这点开销可以忽略；
真有性能问题再引入「页面不可见时暂停重绘，但继续接收数据」。

### 7.2 绘制用 Canvas 还是 DOM

- `number`：纯 DOM（文本更新最便宜）
- `gauge` 环形：**SVG**（`stroke-dasharray` 一行搞定，不用清画布）
- `sparkline`：**Canvas**

sparkline 用 Canvas 的理由：60 个点 × 每秒 20 次更新 × 若干组件，
用 SVG 会产生大量 path 字符串拼接和 GC 压力。Canvas 一个 `clearRect` + `lineTo` 就完事。

### 7.3 数据缓冲

sparkline 的环形缓冲放在**主界面侧**，不在插件侧。这样插件只管推当期值，
换插件（比如从 sysmon 换成别的）时缓冲自然重置，不会串数据。

## 八、与现有机制的关系

| 机制 | 关系 |
|---|---|
| 6.5 iframe 页 | **并存**。复杂交互仍走 iframe，小组件只做轻量展示 |
| 6.6 声明式配置 | **同族**。都是"插件出数据，平台出界面" |
| 能力注册表 | **不参与**。小组件不是可调用能力，别混进 `capability.list` |
| 身份门禁（6.3） | **复用**。声明变化视为信息变化，走「待确认」流程 |
| 扩展统一列表（6.8） | **补充**。列表里标出"提供 N 个小组件" |

## 九、实施顺序

分三步，每步都能独立验收：

### 第一步：只做 `number` + `statusbar`

最小闭环。验证协议、推送链路、渲染。

- 渲染层：`19-widgets.ts`，挂载 `statusbar` 槽
- 服务端：`/api/widgets` 汇总所有插件的声明
- 主控：广播时补 `来源` + 限流
- 验收：写一个测试插件，往状态栏推数字

### 第二步：补齐三种类型 + 三个槽位

- `gauge` / `sparkline`
- `chat.top` / `chat.side`
- 验收：`sysmon` 插件样例——CPU 曲线 + 内存环 + 网速数字

### 第三步：真实插件

- `sysmon`：CPU/内存/GPU（GPU 走 Windows 计数器或 nvidia-smi）
- `netspeed`：测速（主动）与实时速率（被动）分开

> 为什么把插件放最后：协议没稳定前写插件，改一次协议就得改一遍插件。
> 用测试插件验证协议，协议定了再写真的。

## 十、待定问题

1. **`chat.top` 会不会挤掉聊天区？**
   监控条高度约 72px。聊天页本来就有输入区和消息区，加一条可能显得局促。
   备选：默认收纳成一个可展开的细条。**需要做出来看实际效果再定。**

2. **GPU 数据怎么取？**
   Windows 上 `nvidia-smi` 只覆盖 N 卡；通用方案是性能计数器
   `\GPU Engine(*)\Utilization Percentage`。后者要遍历实例并求和，开销不小。
   倾向于：优先 `nvidia-smi`，没有则隐藏该组件（而不是显示 0）。

3. **要不要支持插件自定义颜色/图标？**
   先不做。统一的配色才像"一个产品"，各插件各配色会立刻变成大杂烩。
   真有需求再加 `accent` 一个字段，只允许选主题色而非任意色值。

4. **数据过期怎么办？**
   插件崩了但主界面还在显示最后的值，用户会以为那是实时的。
   方案：超过 `过期` 秒（默认 30）没收到推送，组件置灰并显示「无数据」。
   **这条必须有**，否则监控组件会变成误导性信息。
