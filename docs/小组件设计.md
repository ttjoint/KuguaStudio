# 仪表盘小组件（Widget）设计

> 状态：**设计稿，未实现**
>
> 目标：让插件/模块能把一个小块内容（CPU 曲线、内存环、下载速度数字）**注入主界面**，
> 而不是只能各占一个顶栏标签页。
>
> 依赖：`架构设计.md` 6.5（自带 UI 页）、6.6（声明式配置）、7（苦音协议）

---

## 一、问题

现在插件展示内容的唯一途径是 6.5 的**自带 UI 页**：声明 `"ui": { "entry": "ui/index.html" }`，
WebUI 就给它生成一个**顶栏标签页**，内容塞在 iframe 里。

这套机制适合「打开一个完整功能页」，但用来做「常驻小卡片」有三个硬伤：

1. **占位置**。装 5 个监控插件，顶栏就多 5 个标签。顶栏是导航，不是仪表盘。
2. **看不见**。标签页不激活时 iframe 根本不加载内容（`14-plugin-ui.ts` 里
   `激活时` 才设置 `src`），也就没有「实时显示」可言——用户得先点进去才知道 CPU 多高。
3. **重**。一个"显示下载速度"的卡片，为了它写一整个 HTML 页面，接入成本远高于收益。

所以需要**第二套表面**：小组件。

---

## 二、设计原则

### 2.1 小组件不是缩小的网页

这是最容易走偏的地方。直觉方案是「让插件写一个小 HTML，主界面用 iframe 摆进去」，
但会立刻遇到：

- N 个 iframe = N 个独立 JS 上下文 + N 份 CSS，内存和启动开销随插件数线性涨
- iframe 之间尺寸协商靠 postMessage 往返，第一次渲染必然跳一下
- 插件能做任意 DOM 操作 → 能盖住主界面、能劫持点击、能读不该读的东西

**结论：小组件的内容用数据结构描述，不用 HTML 描述。**
插件只上报「我要显示一个什么」，主界面用自己的组件库渲染。
这条和 6.6 的声明式配置页是同一个思路的延伸：

| 需求 | 方案 | 表达能力 |
|---|---|---|
| 开关、地址、下拉 | 声明式表单（6.6） | 低 |
| 实时数值、曲线、进度 | **小组件（本文）** | 中 |
| 音色试听、模型下载 | iframe 自定义页（6.5） | 高 |

三层按表达力递增，按需选用。常见需求落在前两层，就永远不用碰 iframe。

### 2.2 数据是推的，不是拉的

CPU 占用要每 2 秒刷一次。如果做成「主界面定时调插件」，那么：
主界面得知道插件支持轮询、轮询间隔多少、失败怎么办——这些本来该由插件自己决定。

正确方向是**插件主动推**：插件在自己的采样循环里，采到值就广播一次。
主界面只是被动更新显示。这也符合 2.1：主界面不需要理解「CPU」这个概念。

### 2.3 声明与数据分离

- **声明**（有什么组件、什么类型、放哪）：启动时上报一次，静态
- **数据**（当前值）：高频推送，可丢

分开的理由：声明要走「身份门禁」（6.3）审核，数据不需要；声明变了要重启生效，
数据每分钟变几百次。混在一起会导致高频数据被低频的门禁逻辑拖累。

## 三、形态：三种组件

先只做三种，覆盖绝大多数监控类需求，也不至于让渲染层变成半成品的前端框架。

### 3.1 `number` —— 单个数字

```
┌─────────────────┐
│ 下载            │
│ 12.4 MB/s       │  ← 大号数字
│ 总计 3.2 GB     │  ← 可选副标题
└─────────────────┘
```

```json
{ "id": "net.down", "类型": "number", "标题": "下载",
  "单位": "MB/s", "小数位": 1 }
```

推送：`{ "id": "net.down", "值": 12.4, "副标题": "总计 3.2 GB" }`

### 3.2 `gauge` —— 环形或条形占比

```
┌─────────────────┐
│   ◕ 68%         │  ← 环 + 百分比
│   内存          │
└─────────────────┘
```

```json
{ "id": "mem", "类型": "gauge", "标题": "内存",
  "最大": 100, "单位": "%", "外观": "ring" }
```

`外观`：`ring`（环）/ `bar`（横条）。超阈值变色由主界面统一处理（`警示` / `危险` 阈值可选）。

### 3.3 `sparkline` —— 时间序列小曲线

```
┌─────────────────┐
│ CPU  34%        │
│  ╱╲    ╱╲╱      │  ← 最近 N 个点
└─────────────────┘
```

```json
{ "id": "cpu", "类型": "sparkline", "标题": "CPU",
  "最大": 100, "单位": "%", "点数": 60 }
```

数据是**追加**而非覆盖：推送 `{ "id": "cpu", "值": 34.2 }`，主界面自己维护最近 `点数` 个值。
插件不需要每次推一整条数组，省带宽也省得插件自己维护环形缓冲。

> 为什么不做 `table` / `list` / `chart`：
> 表格看进程列表、多轴折线图这类需求真实存在，但它们更适合 iframe 页。
> 小组件的定位是「扫一眼就知道」，不是「展开研究」。

## 四、职责分界：插件说内容，GUI 说形式

这是整个设计最关键的划分。

| 归插件管 | 归 GUI 管 |
|---|---|
| 块里显示什么（数值、单位、曲线） | 放在哪（顶栏 / 侧栏 / 状态栏 / 浮窗） |
| 数据怎么采、多久推一次 | 用什么形态（大卡 / 横条 / 浮窗） |
| 哪个块最重要（显著度） | 多大、怎么排列、几个一排 |
| 哪些块属于同一组 | 屏幕窄了怎么堆、宽了怎么展开 |

**插件不许写“放到 chat.top”。** 那是 GUI 的事。插件在另一台机器上
可能跑在完全不同的前端上，它无从知道「top」在哪、屏幕多宽、
用户把侧栏展开还是折叠了。

### 4.1 那 GUI 怎么知道该把 CPU 和内存放一起

靠插件只提两件事：**分组** + **显著度**。

```json
{ "id": "cpu", "type": "sparkline", "title": "CPU",
  "group": "sysmon.系统", "prominence": "primary" }
```

- **`group`**：同一个组的小组件，GUI 应当把它们摆在一起（同一横排 / 同一卡片内）。
  不填则默认等于插件名——一个插件的组件天然成组。
  填了就是跨插件合并，比如另一个插件的 GPU 监控可以声明 `"group": "sysmon.系统"`。
- **`prominence`**：`primary` / `normal` / `secondary`，只表达相对重要性，
  不表达位置。

### 4.2 显著度怎么被 GUI 解释

| 显著度 | 含义 | GUI 的默认处置（可改） |
|---|---|---|
| `primary` | 用户最常看的那一两个数 | 大卡，放在最显眼处（聊天页顶部横条） |
| `normal` | 常规信息 | 中等大小，主区域 |
| `secondary` | 细节、偶尔才看 | 窄条或状态栏，可默认折叠 |

这是**建议而不是指令**。GUI 完全可以在屏幕窄时把所有 `primary` 也压成窄条，
或者在用户手动拖动后忽略显著度。

关键点：显著度是**稳定语义**（重要性），槽位是**易变实现**（像素位置）。
插件只能声明前者，否则它就跑在了平台演化前面。

### 4.3 每个插件的 primary 有上限

如果所有插件都把自己的组件标成 `primary`，「primary」就失去意义了。

- 单个插件最多 **2 个** `primary`，超出部分自动降为 `normal` 并记日志
- GUI 也保留最终裁决权：若 `primary` 总数 > 4，按插件名排序取前几个

这跟第七节的限流一样：契约靠平台守，不能指望插件自觉。

## 五、协议

### 5.1 声明

插件在 `kugua-plugin.json` 里加一个字段（模块则在握手时的 `界面` 旁边加 `小组件`）：

```json
{
  "name": "sysmon",
  "ui": { "title": "系统监控", "entry": "ui/index.html" },
  "widgets": [
    { "id": "cpu", "type": "sparkline", "title": "CPU",
      "unit": "%", "max": 100, "points": 60,
      "prominence": "primary", "warn": 80, "danger": 95 },
    { "id": "mem", "type": "gauge", "title": "内存",
      "unit": "%", "max": 100, "appearance": "ring",
      "prominence": "primary" },
    { "id": "net.down", "type": "number", "title": "下载",
      "unit": "MB/s", "decimals": 1,
      "prominence": "secondary" }
  ]
}
```

注意这里**没有 `slot`、没有 `order`、没有 `size`**。插件只说：

1. 我有哪几个块（`id` / `type` / `title` / 显示参数）
2. 哪个重要（`prominence`）
3. 哪些成组（`group`，不填则等于插件名）

放哪里、多大、什么形状，全由 GUI 决定（第四节）。

> 清单文件里**用英文键**（`type`/`title`/`prominence`），因为 `kugua-plugin.json`
> 是对外的、会被第三方照着写；而运行时握手载荷继续用中文键，那是内部协议。
> 这和「SDK 公开 API 纯英文」是同一条约束。

### 5.2 数据推送

插件用现成的广播能力推，不新增通道：

```ts
ctx.broadcast("widget.data", { id: "cpu", value: 34.2 });
```

模块在苦音总线上：

```ts
客户端.broadcast("widget.data", { 来源: "sysmon", id: "cpu", 值: 34.2 });
```

主界面通过 `window.kugua.onBus` 收到后分发给对应组件。

**为什么要带 `来源`**：`id` 只在插件内部唯一（`cpu` 这个名字谁都想用），
全局唯一键是 `来源 + id`。主控收到广播时统一补上 `来源`，插件自己不许填
（否则可以冒充别的插件的数据）。

### 5.3 限流

高频推送是必然的（有人会每 100ms 推一次）。两条限制：

- **单插件每秒最多 20 次** `widget.data`，超出丢弃并计数
- 丢弃计数在插件管理页显示，让插件作者自己发现写错了

丢弃而不排队：旧数据没有价值，排队只会让显示越来越滞后。

## 六、用户自定义布局

插件说内容和优先级，GUI 决定形式；**用户可以把 GUI 的决定再改掉**。

### 6.1 状态存哪里

存在 `kugua.config.json` 的 `widgets` 节（平台维护，插件不碰）：

```json
{
  "widgets": {
    "当前方案": "日常",
    "方案": {
      "日常": {
        "展示": "自动",
        "覆盖": {
          "sysmon.cpu":      { "区域": "顶部", "外形": "大卡", "顺序": 10 },
          "sysmon.net.down": { "隐藏": true }
        }
      },
      "专注写东西": {
        "展示": "仅状态栏",
        "覆盖": {}
      }
    }
  }
}
```

- **`方案`**：可命名的布局方案，至少一个（叫「默认」）。
- **`展示`**：方案级形态预设——`自动` / `紧凑` / `详细` / `仅状态栏`。
  这是最快满足“我现在不想要大块内容”的旋钮，不用逐个改。
- **`覆盖`**：单个小组件的用户手动指定。**只存用户改过的项**，
  没改过的不入库，始终跟随 GUI 的自动决策。

键是全局唯一的 `来源.id`（`插件名.id`）。

为什么不用单独文件 / localStorage：

- **localStorage**：换设备/换浏览器就没了；桌面壳和浏览器两个入口也各自一份
- **单独文件**：又多一个要备份、要迁移、要写合并逻辑的东西
- **放进主配置**：已经有两层合并（主 + local）、已有透传未知节的保障、
  用户已经知道配置在哪。布局本质就是配置。

### 6.1.1 为什么做成“多套方案”而不是一套

同一套布局不可能同时适合所有场景：写东西时要安静（全塞状态栏），
盯任务时要详细（作业队列、内存都在眼前），录屏时要干净。

只给一套布局，用户就得每次手动调一遍——手动调 5 个组件换一次场景，
没人会真去用，于是全部退回默认。**多套方案 + 一键切换**才让这个功能真的被用起来。

约束：

- 方案切换**不是插件的事**，也不通知插件（插件一直推数据，不管展示在哪）
- 新建方案时从当前方案复制，再手改，不从空白开始
- 删方案时若删的是当前方案，自动落到「默认」
- **至少保留一套**，不允许删光

### 6.2 哪些能改

| 能改 | 不能改 |
|---|---|
| 外形（大卡 / 横条 / 窄条 / 浮窗） | 类型（`number` 还是 `gauge`） |
| 区域（顶部 / 侧栏 / 状态栏 / 浮层） | 数据来源 |
| 顺序 | 组归属 |
| 隐藏 / 显示 | 插件声明的内容 |
| 浮窗的具体坐标与大小 | |

**类型不可改**：那是插件代码的实现细节，用户改了也没意义。
**组归属不可改**：那是插件对“这些数据相关”的判断。用户真想拆，
拖拽/选区域已经能拆开。

### 6.3 设置页里的「仪表盘布局」

布局编辑界面放在**设置页**，一个新分组「仪表盘」，紧跟在「模块管理」后面。

这里跟「插件配置」是有意分开的两件事，不能混：

| | 配置页（6.6） | 仪表盘布局（本节） |
|---|---|---|
| 管什么 | 插件自己的参数（API 地址、音色、阈值） | 这些组件在我屏幕上怎么摆 |
| 存哪 | `kugua.config.json` → 模块名下 | `kugua.config.json` → `widgets` |
| 归谁 | **插件**解释含义 | **平台**解释含义 |
| 插件能读吗 | 能 | **不能**（也不应该关心） |

插件不应该知道用户的屏幕宽多少、把侧栏收起来了、现在是写东西模式。
把布局混进插件配置，等于让插件对 GUI 细节产生依赖。

#### 界面形态

```
┌─ 仪表盘 ────────────────────────┐
│ 方案  [日常 ▾] [+ 新建] [重命名] [删] │
│ 全局  [自动 ▾]                        │
│────────────────────────────────│
│ ☰ sysmon.cpu        CPU       顶部/大卡  [眼睛] │
│ ☰ sysmon.mem        内存      顶部/大卡  [眼睛] │
│ ☰ sysmon.net.down   下载      状态栏/窄条 [眼睛] │
│   ↳ 来源：系统监控（在线）            │
│────────────────────────────────│
│ [恢复此方案为默认]  [清理失效项 (1)]  │
└────────────────────────────────┘
```

要点：

- 每行带**拖拽柄**（☰），在设置页里也能调顺序，不必回到主界面拖
- 行内显示**来源插件名与在线状态**，插件挂了这里能一眼看出
- 失效项（插件已不存在）聚到底部，灰显 + 勾选批量清理
- 改完**即时生效**，不需要重启（只重渲染，不碰插件进程）

### 6.4 怎么改

两个入口，覆盖不同场景：

1. **主界面拖拽**（主场景）：小组件拖到另一个区域、在区域内拖排序。
   - 拖拽中显示插入位置指示线
   - 跨区域拖动时目标区域高亮
   - 松手写盘（防抖 500ms，不是每动一下就写）
2. **设置页列表**（兵底）：见 6.3。拖拽在触屏/小窗口不好用时靠这里，
   也能看到“已隐藏但插件还在推数据”的项，方便恢复

3. **一键恢复默认**：清掉该项的用户覆盖，回到 GUI 的自动决策。
   注意不是回到插件声明的 `prominence`——那本来就是 GUI 的输入，不是输出的布局。

### 6.5 插件消失后怎么办

插件被卸载/禁用，它在配置里的布局项就成了孤儿。两种处理：

- **不自动删**。保留着，万一插件只是暂时禁用、重新装回来时布局还在
- **设置页标为“失效”**，提供“清理失效项”按钮

自动删是不可逆的，而保留的成本只是一个 JSON 键。

### 6.6 与插件声明变更的冲突

插件升级后改了 `prominence` 或组件集合，但用户已经摆好了——**以用户为准**。

这靠两条规则保证：

1. 用户覆盖按 `来源.id` 存，插件改 `prominence` 不影响已覆盖的项
2. 未被用户改过的项，继续跟随 GUI 的新自动决策

插件删了某个组件：布局项成孤儿，按 6.5 处理（保留 + 标失效）。
插件新增组件：没有覆盖项，直接按自动布局排。

**插件没有任何手段推翻用户的布局**，这是有意的。

## 七、给插件开发者的界面结构 API

���疑点很对：小组件一旦成为机制，就需要一份**稳定的结构契约**，
否则每个插件都得去猜“我能填什么值”。

### 7.1 契约在哪

不另建一套 API 文档，**直接复用现有的类型包**：

| 消费者 | 拿到契约的途径 |
|---|---|
| Node 插件（TS） | `@kugua/plugin-sdk` 导出 `小组件声明` 类型 + 常量 |
| Node 模块（TS） | `@kugua/module-kit` 导出同名类型 |
| Python / 其他语言 | `sdk/README.md` 的表格 + `sdk/python/nigane.py` 里的常量 |
| 手写 JSON 的人 | `docs/小组件设计.md` 本节的表 |

**单一事实来源是 TypeScript 类型**，其他语言 SDK 与文档都由它行生。
这跟现有 `配置声明` 的做法一致，不另造轮子。

### 7.2 契约内容

```ts
// @kugua/plugin-sdk

/** 小组件类型（新增值属于破坏性变更，不轻易加） */
export type 小组件类型 = "number" | "gauge" | "sparkline";

/** 显著度：只表达重要性，不表达位置 */
export type 显著度 = "primary" | "normal" | "secondary";

export interface 小组件声明 {
  /** 插件内唯一，只能 [a-z0-9._-]。全局键 = 插件名 + "." + id */
  id: string;
  类型: 小组件类型;
  标题: string;

  /**
   * 显著度，默认 normal。
   *
   * **它只是建议**：GUI 可能因为你把侧栏折叠了而把 primary 也压成窄条。
   * 别把它当布局指令用。单插件最多 2 个 primary。
   */
  显著度?: 显著度;

  /**
   * 分组：同组的组件 GUI 应摆在一起。默认 = 插件名。
   * 填别的字符串可以跟其他插件的组件合并成组。
   */
  分组?: string;

  单位?: string;
  小数位?: number;
  /** gauge / sparkline 的最大值，默认 100 */
  最大?: number;
  /** sparkline 保留多少个点，默认 60，上限 300 */
  点数?: number;
  /** gauge 外观，默认 ring。**这是外观建议，GUI 可忽略** */
  外观?: "ring" | "bar";
  /** 超过此值变黄 */
  警示?: number;
  /** 超过此值变红 */
  危险?: number;
  /** 多少秒没推送就置灰为「无数据」，默认 30，最小 5 */
  过期?: number;
}

/** 推数据（插件侧） */
export function 推小组件值(宿主: 广播能力, id: string, 值: number, 副标题?: string): void;
```

注意**没有 `slot`、`order`、`size`、`width` 这类字段**。它们一旦进了契约，
就再难拿掉（要考虑兼容），而布局是 GUI 最可能变的部分。

### 7.3 版本兼容规则

| 变更 | 性质 | 处理 |
|---|---|---|
| 新增类型（如 `bar`） | 破坏性 | 需主版本号；旧平台拒该声明并记日志 |
| 新增可选字段 | 兼容 | 旧平台忽略 |
| 新增显著度取值 | 兼容 | 旧平台当 `normal` |
| 重命名字段 | 破坏性 | 不做，宁可加别名 |

注意表里**没有“新增槽位”这一行**——因为槽位不在契约里。
GUI 怎么分区域、加不改区域，不需要插件知道，也就不需要走兼容流程。
这是第四节职责分界带来的直接好处。

**旧平台遇到不认识的类型**：拒绝该条声明，其余照常。
不能默默当 `number` 渲染——那会让用户看到莫名其妙的东西。

### 7.4 插件不需要知道的

契约只覆盖“声明什么 / 推什么”。以下实现细节**不进契约**，平台可随时改：

- **放在哪个区域、多大、什么形状**（包括“大卡/横条/浮窗”这些概念）
- 渲染用 DOM / SVG / Canvas（目前 `gauge` 用 SVG、`sparkline` 用 Canvas）
- 环形缓冲存在哪侧
- 限流的具体阈值（目前 20 次/秒）
- 拖拽交互怎么实现、布局怎么存

插件只关心两件事：**声明一次，然后推值**。

## 八、安全边界

小组件比 iframe 页容易守，因为它不执行插件代码。但仍有三处要防：

| 风险 | 处理 |
|---|---|
| 插件上报恶意 HTML 当标题 | 标题/副标题一律 `textContent`，**绝不 innerHTML** |
| `id` 里塞奇怪字符 | 只允许 `[a-z0-9._-]`，其余拒绝该声明 |
| 声明数量爆炸 | 单插件最多 12 个小组件，超出截断并记日志 |
| 冒充其他插件推数据 | 主控强制覆盖 `来源` 字段 |
| 跨站请求伪造广播 | 广播走 `/api/broadcast`，已有同源检查 |

**不做的**：不搞沙箱隔离。小组件不放 iframe 正是为了性能，
而它不执行插件代码这个前提让隔离失去意义。

## 九、渲染实现要点

### 9.1 惰性挂载，但**不**惰性订阅

和 iframe 页不同，小组件在页面加载后**全部**挂载（哪怕用户当前在知识库页）。
原因：数据推送是需要有人接的，如果切回聊天页才订阅，那切过去的瞬间是空白，
用户得等第一次推送——体验上就是「卡一下」。

代价是所有小组件始终在更新 DOM。对 10 个以内的组件，这点开销可以忽略；
真有性能问题再引入「页面不可见时暂停重绘，但继续接收数据」。

### 9.2 绘制用 SVG 还是 Canvas

- `number`：纯 DOM（文本更新最便宜）
- `gauge` 环形：**SVG**（`stroke-dasharray` 一行搞定，不用清画布）
- `sparkline`：**Canvas**

sparkline 用 Canvas 的理由：60 个点 × 每秒 20 次更新 × 若干组件，
用 SVG 会产生大量 path 字符串拼接和 GC 压力。Canvas 一个 `clearRect` + `lineTo` 就完事。

### 9.3 数据缓冲

sparkline 的环形缓冲放在**主界面侧**，不在插件侧。这样插件只管推当期值，
换插件（比如从 sysmon 换成别的）时缓冲自然重置，不会串数据。

## 十一、实施顺序

分四步，每步都能独立验收。

### 第一步：协议 + 三种类型 + 自动布局 + 布局存储　✅ 已完成

实际实现比原计划多做了一步（三种类型一起做了）——协议定型后再拆开写
反而要把渲染函数改两遍。

- `packages/nigane/src/widget-protocol.ts`：声明类型、归一、限流常量
- `packages/main/src/widgets.ts`：注册表（运行时）+ 布局存储（`widgets` 节）
- 主控接口：`nigane.widgets.declare` / `unregister` / `list` / `config.set`
- plugins 模块：读清单 `widgets` 代报，安装/重载/卸载时同步
- 渲染层 `19-widgets.ts`：三种类型 + 自动布局 + 过期置灰
- 限流：`packages/webui/src/widget-throttle.ts`（20 次/秒，超出丢弃）
- 样例插件：`examples/widget-demo`（复制到 `plugins/sysmon` 即可运行）

**实现时才发现的三个问题**（设计稿里没写对）：

1. **`来源` 不能取自信封。** 插件跑在 plugins 模块进程里、共用同一个连接，
   所以信封 `from` 永远是 `plugins`。改成 plugins 模块在 `ctx.广播` 时注入
   真实插件名，主控再按连接身份盖章（非 plugins 的发送者以自己名字为准）。
2. **loader 丢字段。** 原来写 `插件类.插件元数据 ?? 记录.元数据`，SDK 那边
   没重复写 `widgets` 就整个没了。改成两者合并，代码优先但清单字段保留。
3. **在线状态对不上。** 模块上线事件的名字是 `plugins` 而非插件名，靠不上；
   改成「能发声明就算在线」。

### 第二步：真实监控组件 + 响应式降级

- 响应式：窗口窄了自动降级成窄条（现在只按显著度决定，不看宽度）
- GPU：优先 `nvidia-smi`，没有则不声明该组件
- 网速：Windows 取不到网卡计数器，暂不提供（见下）

### 第三步：用户自定义（拖拽 + 多方案）

- 主界面拖拽调区域/顺序
- 设置页「仪表盘」分组：方案切换/新建/删除、行内拖拽、失效项清理
- 验收：建两套方案（日常 / 专注），一键切换生效

### 第四步：真实插件

- `sysmon`：CPU/内存/GPU（GPU 走 Windows 计数器或 nvidia-smi）
- `netspeed`：测速（主动）与实时速率（被动）分开

> 为什么把插件放最后：协议没稳定前写插件，改一次协议就得改一遍插件。
> 用测试插件验证协议，协议定了再写真的。

## 十二、延伸议题：整个前端可拼装？

这是另一个量级的问题，单独说清。

### 12.1 现在的前端到底是什么状态

实测（不计 node_modules）：

| 指标 | 数值 |
|---|---|
| 渲染层总行数 | 9621（parts/ 24 个文件） |
| 跨 part 的 import | `03-preview` 被引 20 次，`07-explorer`/`06-shell`/`02-chat-core` 各 10 次 |
| 直接 `getElementById` | `07g-explorer-editor` 69 处，`07-explorer` 46 处，`03-preview` 38 处 |

结论很明确：**部件只是在文件名上分开了，实际是一块 9600 行的单体。**
它们共享同一个全局 DOM、同一份隐式状态、彼此直接 import。

所以“把现有组件模块化”不是把文件拆一拆，而是：

1. 每个部件自己拥有 DOM 子树（现在是 `getElementById` 漫天抓）
2. 每个部件有显式输入输出（现在靠全局变量隐式传递）
3. 有一个布局容器按配置决定实例化哪些、放哪里（现在写死在 index.html）

第 1、2 条是真难点，第 3 条反而最便宜。

### 12.2 我不建议现在接这个活

理由不是“工作量大”这么笼统，而是具体的：

- **没有驱动需求**。小组件的驱动需求是“插件要显示数据”，真实且当下就痛。
  “整个界面可拼装”的驱动需求目前是“听起来很灵活”——它不解决任何现有问题。
- **改错了代价高**。9600 行单体重构期间所有其他功能都得停，或者两套并行。
- **范围会失控**。编辑器、知识库浏览器、聊天流——每一块的“可拼装”含义都不同。
  聊天流本来就是个插件化的东西（消息类型），知识库浏览的“拼装”又是另一回事。

### 12.3 更实际的路径：先让小组件机制变成“内部组件机制”

本文设计的小组件机制，其实就是一个小型的可拼装系统：

- 声明式描述（`type` + `title` + `prominence`）
- 容器按声明实例化
- 布局状态可存、可改

如果把它做得足够干净（组件注册表 + 容器 + 布局状态），
**以后把内置界面（作业列表、日志尾）也注册成小组件**就是自然的一步，
而不需要重写整个前端。

建议的推进方式：

| 阶段 | 做什么 | 风险 |
|---|---|---|
| 现在 | 小组件机制（本文档） | 低，新代码 |
| 以后 | 把“作业队列摘要”“日志尾”做成内置小组件 | 低，新代码 |
| 再以后 | 新增可放小组件的“面板页”（新的视图，不动现有页） | 中 |
| 最后才考虑 | 把聊天/知识库拆成组件 | 高，需单独提案 |

**关键是：每步都是加新东西，不是改旧东西。** 等到小组件机制真的把
“拼装”这件事验证透了，再讨论要不要把老界面搬过去——那时候会有真实反馈，
而不是凭想象设计。

### 12.4 如果真要做，前置条件

到那时候先得有两样东西，否则必定失败：

1. **状态管理方案**。现在 9600 行共享全局变量，拆成组件后跨组件状态怎么同步
   是头号难题。没有答案之前，拆了也会缠回去。
2. **一个真实的重构试点**。先拆一个中等耦合度的（如“作业页”159 行）
   验证模式可行，再谈全面推广。

一句话：**别为一个还没具象化的需求提前重构。**

## 十三、待定问题

1. **主区域多高才不挤？**（已能做出来看，待观察实际观感）
   当前实现：`primary` 渲染成大卡放顶部，`normal` 放顶部横条，
   `secondary` 压缩进底部状态栏。这个分配是否合理要看日常使用。
   备选仍是「`primary` 默认开，其余折叠成细条可展开」。

2. **GPU 数据怎么取？**
   Windows 上 `nvidia-smi` 只覆盖 N 卡；通用方案是性能计数器
   `\GPU Engine(*)\Utilization Percentage`。后者要遍历实例并求和，开销不小。
   倾向于：优先 `nvidia-smi`，没有则隐藏该组件（而不是显示 0）。

3. **要不要支持插件自定义颜色/图标？**
   先不做。统一的配色才像“一个产品”，各插件各配色会立刻变成大杂烩。
   真有需求再加 `accent` 一个字段，只允许选主题色而非任意色值。

4. **数据过期怎么办？**　✅ 已实现
   超过 `过期` 秒（默认 30）没收到推送，组件置灰并显示「无数据」。
   **从未收到过数据的也从挂载时刻起算**——否则「声明了但取不到数」
   会永远停在「—」，用户分不清是「还没采到」还是「这功能根本不可用」。

5. **方案切换多久生效？**
   切方案要重建 DOM，如果监控组件很多会有一次闪。
   倾向于：切方案时只在有差异的组件上搬家，不做全量销毁重建。
   **第一步不做，第三步遇到再说。**

6. **浮窗形态要不要做？**
   用户可能想把 CPU 监视器改成无边框浮窗挂在桌面。这需要记住坐标、
   处理多屏、还得跟桌面壳通信——工作量不小。
   倾向：**第一阶段不做**，先把卡片形态做扁。
   真做了也只在桌面壳里支持，浏览器入口降级为卡片。
