# 作业与插件长任务

> 本文说明「一个能力怎么变成后台作业」以及「插件怎么发起、怎么续跑」。
> 协议层的 Job 动作表见 [架构设计.md](架构设计.md) 第五节；本文只讲**契约细节**和**为什么这么定**。

## 一、什么时候该用作业

判据只有一条：**这件事会不会超过一次请求能等的时间**。

| 场景 | 走什么 | 为什么 |
|---|---|---|
| 处理一张图、查一次天气 | `request` | 毫秒到秒级，答案就是结果本身 |
| 一次转码、一次批量抠图（3000 张） | 作业 | 一次请求等十分钟，指令那边早超时了，而模块其实还在跑 |
| 定时任务里跑上面的批量 | 作业（自动改写） | 见第四节 |
| 插件里跑一个外部程序 | 作业 | 插件的 `await` 超时不会杀掉子进程，会留下孤儿进程 |

**最容易犯的错**：把批量写成普通 `request`。表现是「指令超时」，但模块那边并没有停——
用户以为失败了，实际磁盘上的文件已经被改了。这种「报错但成功了」比「报错且没做」难查得多。

## 二、能力声明里的两个字段

```jsonc
{
  "名称": "image.batch",
  "模块": "image",
  "参数": { "type": "object", "properties": { "文件列表": { "type": "array" } } },

  // 1) 能脱离请求生命周期，在子进程里跑
  "可作业": true,

  // 2) 怎么起这个子进程（`{参数键}` 占位）
  "执行": {
    "命令": "node",
    "参数": ["{文件列表}", "{动作名}", "{输出目录}"],
    "shell": false
  }
}
```

### 为什么 `执行` 写在能力声明里，而不是 job 模块里

`执行` 描述的是「**这个能力**怎么启动」，它必须跟能力的实现一起演化：换 ffmpeg 的路径、
加一个命令行开关、把参数拆成两个——这些都是能力作者的事。job 那边抄一份就是第二份真相，
改了这边忘了那边，表现是「作业跑的是旧命令」，而且完全没有征兆（子进程正常启动、正常退出、
结果不对）。

### `可作业` 与 `长任务` 为什么是两个字段

- `长任务` = 「这个调用要等很久」。可以在原模块里**同步等**，只是超时时间放宽到 10 分钟。
- `可作业` = 「这个调用能**脱离**请求生命周期在子进程里跑」。要求命令可序列化、不依赖会话状态。

混成一个字段的后果：一个要读编辑页 base64 的图片动作会被误判为「可批量离线」，
转出来的作业起来就 failed，而用户看到的是「这个动作支持批量」的入口。

### 占位符规则

| 写法 | 替换成 |
|---|---|
| `{参数名}` | 该参数的值（字符串、数字都按 `String()`） |
| `{参数}` | 整个参数的 JSON |
| 不存在的键 | **原样保留** `{不存在的键}` |

最后一条是刻意的：静默替换成空串的后果更坏——用户看到的是「少了一个参数」，
而不是「占位符名字写错了」。前者会去改调用，后者才会去改声明。

占位符替换用 `split/join` 而不是 `replace`：`replace` 只换第一个，
`"{path}"` 与 `"{path}{path}"` 同时出现时，第二个会原样传给子进程。

### 外部模块的 `exec` / `execute`

Python / Go 写的模块习惯写 `exec`。能力归一那一步会把它们映射成 `执行`，
所以两种写法都能被 job 认出来。不映射的话，报的是「未声明 执行」——
明明声明了，只是键名不同，这种错误很难自己看出来。

不能转作业的能力**不要写** `执行`。job 会返回明确提示「此能力未声明 执行，请用 `命令` 直接启动」，
而不是抛一个让人以为 job 坏了的异常。

## 三、断点续跑契约

作业进程通过三个环境变量知道自己的身份：

| 变量 | 含义 |
|---|---|
| `KUGUA_JOB_ID` | 作业 id，同一个作业重跑/续跑时**不变** |
| `KUGUA_JOB_ATTEMPT` | 尝试次数，从 1 开始，每次续跑 +1 |
| `KUGUA_JOB_PROGRESS` | 进度文件的绝对路径 |

**这就是全部契约。** 脚本只要按这三个值写自己的进度文件，就能续跑：

```js
const 进度 = process.env.KUGUA_JOB_PROGRESS;
const 已做 = existsSync(进度) ? new Set(readFileSync(进度, "utf8").split("\n")) : new Set();
for (const 文件 of 文件列表) {
  if (已做.has(文件)) continue;
  await 处理(文件);
  appendFileSync(进度, 文件 + "\n");
}
```

为什么不走命令行参数：环境变量不会被 shell 引号规则吃掉，也不会弄脏日志里那一行命令。

这三个值**覆盖**调用方自己传的同名变量。理由很实际：如果脚本能自己写
`KUGUA_JOB_ATTEMPT`，它就能骗掉续跑逻辑跳过还没做完的部分。

### 重跑 vs 续跑

| 动作 | id | 尝试次数 | 日志 | 用在哪 |
|---|---|---|---|---|
| `job.rerun` | **新 id** | 从 1 开始 | 新文件 | 「上次参数不对，重来一遍」 |
| `job.continue` | 同 id | +1 | **追加** | 「上次跑到一半断了，接着跑」 |

`job.continue` 只在作业是**可续跑**状态时可用（`cancelled` / `timeout`）。

`done` 和 `failed` 不算可续跑：`done` 再续是重复劳动；`failed` 通常意味着参数不对，
从头重跑（`job.rerun`）才是对的。`failed` 但不续跑看着反直觉，但「失败了一半就接着跑」
在脚本没写进度文件时会让它默默跳过所有已完成项、直接报成功——比报错更坏。

## 四、定时任务怎么自动改写

`packages/modules/scheduler/src/handlers.ts` 里有两张名单：

```ts
const 强制作业动作 = ["job.start", "job.rerun", "job.continue"];
const 建议作业动作 = ["image.batch"];
```

命中这两个名单的 `request` 动作，在**录入时**就被改写成 `job.start`：

```
{ to: "image", action: "batch", params: {...} }
        ↓
{ to: "job", action: "job.start",
  params: { 能力名: "image.batch", 能力参数: {...},
            来源: "scheduler", 发起者: "scheduler:image" } }
```

- `来源` 固定 `scheduler`，作业列表据此区分「我点的」和「半夜自己跑的」。
- `发起者` 带模块名前缀，`job.done` 事件据此知道把结果推给谁。
- 改写在录入时做，不是触发时做：触发时是半夜，出错没人看得到；录入时用户就在界面上。
- 已经带模块前缀的动作名（`image.batch`）不重复拼，否则得到 `image.image.batch`。

## 五、插件的长任务

插件不直接 `spawn`，一律走 `job.start`：

```js
const { id } = await 宿主.请求("job", "job.start", {
  能力名: "image.batch",
  能力参数: { 文件列表, 动作名: "removeBg" },
  发起者: `plugin:${this.name}`,
  来源: "plugin",
});
```

**为什么插件不能自己 spawn**：插件跑在平台进程里，平台一重启插件就没了，
但它 `spawn` 的子进程是独立进程，会留在系统里。走 job 的话
平台退出时 `关闭()` 会按进程树收掉（`杀进程树`），不会留孤儿。

副作用也有好处：插件不用自己写进度、日志、取消、历史，作业页直接能看到。

插件**不需要**声明 `执行`——除非插件自己也提供能批量跑的能力。那种情况下
`执行` 写在插件的能力声明里，与内置模块完全一样。

## 六、已知限制

- **POSIX 上的进程树终止是权宜的**：Windows 那边是 `taskkill /PID <pid> /T /F`，连子进程一起收；
  POSIX 目前只杀根进程（子进程如果自己 fork 了会留下来）。真要修得拉进程组或 `pkill -P` 递归。
- **进度文件格式由脚本自己决定**，job 只负责给出路径（并用新的 `KUGUA_JOB_PROGRESS` 传给它），
  不解析内容。所以作业页上的百分比只能来自脚本自己上报，job 不猜。
- `job.continue` 不检查磁盘是否真的一致——脚本得自己保证「写到进度文件里的那一条
  是真的做完了」。先写进度后干活，就会漏掉那一条。
