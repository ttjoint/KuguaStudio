# 苦瓜工作室 架构设计

> 本文是本项目的顶层蓝图，定义"苦瓜工作室"是什么、由哪些层组成、各层之间如何协作。
> 具体编码规范、协议字段、目录约定见《开发细则.md》；知识库见《知识库设计.md》；对外互操作见《互操作设计.md》；
> 分阶段施工任务见《改造清单.md》。

## 一、定位

苦瓜工作室（KuguaStudio，KS）是一个**纯本地的个人自动化工作台**：

- 常驻宿主后台，随系统启动；
- 以**可插拔模块**承载功能（图片/GIF 处理、文本工具、历法、脚本任务、爬虫、系统任务……）；
- 各模块通过**统一信息总线**通信与协同；
- 提供**中文指令**与**图形界面**两种入口，且同一功能自动同时具备"指令 / 界面 / 定时 / 开机 / 外部接口"多种使用方式；
- 内置**本地知识库（MKG）**，以标签图 + 全文检索替代一部分 Windows 资源管理器，统一管理图片、多媒体、文本段与学术资料；
- 能方便地执行与调度**临时脚本任务**（Python / 爬虫 / 安全测试等），并**外联其他小项目**。

> 注意：本项目**不是** AI 应用平台。AI 只是一项可选的外部能力（通过统一网关调用），
> 核心价值在于"本地功能可插拔 + 可调度 + 可检索 + 可互操作"。

## 二、设计原则

1. **本地优先**：默认不依赖任何云服务；网络功能显式声明、可关闭。
2. **文件系统为真源**：知识库只是索引与标签层，不搬迁、不破坏原始文件；标签可随文件携带（侧车）。
3. **进程隔离**：每个模块是独立进程，崩溃不影响主控与其他模块。
4. **一处声明，多处暴露**：一个功能只在"能力注册表"声明一次，自动派生全部入口（见第四节）。
5. **跨语言**：模块可以用 TypeScript、Python 或任意可执行文件实现，只要能讲统一契约。
6. **最小依赖**：优先 Node 内置能力与单文件 SQLite；不引入需要长期运维的中间件。
7. **权限显式化**：任何涉及文件写、网络、执行外部程序的模块必须在能力声明里写明权限，危险能力默认不对外暴露。
8. **可演进而非推倒**：总线协议保持向后兼容；新增能力通过扩展而非破坏既有语义。

## 四、能力注册表（核心）

### 4.1 为什么需要它

现状问题：同一功能在指令、GUI、调度、开机、外部调用里各写一遍，改一处漏三处。
能力注册表把"功能"变成一等公民：**声明一次，五处自动可用**。

### 4.2 能力声明

```jsonc
{
  "名称": "image.gifUnzip",          // 全局唯一，建议 `模块.动作`
  "模块": "image",                    // 提供者模块名
  "动作": "image.gifUnzip",           // 苦音 action，缺省等于名称
  "标题": "GIF 拆帧",
  "说明": "把 GIF 拆成多张图片返回",
  "中文指令": ["gif拆帧", "拆gif"],
  "参数": {                           // JSON Schema（object）
    "type": "object",
    "properties": { "base64": { "type": "string" } },
    "required": ["base64"]
  },
  "权限": ["filesystem:read"],        // 见 4.5
  "危险": false,                       // 危险能力默认不暴露给 MCP
  "长任务": false,                     // true 走 Job 语义（第五节）
  "暴露": { "指令": true, "GUI": true, "定时": true, "MCP": true }
}
```

### 4.3 五种入口的派生

| 入口 | 来源 | 行为 |
|---|---|---|
| 中文指令 | `中文指令[]` + `参数` | 解析文本 → 参数 → 调用能力 |
| GUI | `标题/说明/参数` | WebUI 命令面板项 / 按钮 / 表单 |
| 定时任务 | `暴露.定时` | scheduler 的候选动作 |
| 开机任务 | `暴露.定时` + 位置=启动 | 登录后自动执行一次 |
| 外部接口 | `暴露.MCP` | MCP `tools`，JSON Schema 直接复用 |

### 4.4 注册与调用

- 模块在握手（`hello`）时携带 `capabilityDefs`（能力声明数组）与 `capabilities`（能力名列表）；主控汇总为全局注册表。
  - **能力名无需手写**：`NiganeClient` 在握手时自动合并「能力声明（取 `动作 ?? 名称`）
    + 已注册的请求动作（`onRequest`）」作为 `capabilities`（除非调用方显式传入）。
  - 未提供显式声明时，主控由 `capabilities` 名称自动合成基础能力（名称即动作、GUI 可见）；
  - 与模块同名的自标识（如 `capabilities: ["webui"]`）不注册为能力。
- 因此模块只需**声明能力（富元数据）+ 注册处理器**两件事，不再维护第三份能力名清单，
  也不会出现「清单与实际注册动作漂移」。
- 运行时变更（上下线/热插拔）通过事件 `capability.changed` 广播，各入口刷新。
- 主控内置动作：`capability.list` / `capability.get` / `capability.call` / `capability.command`。
- 统一调用：`registry.invoke(名称, 参数)` → 主控经 `NiganeServer.request` 路由到 `模块.动作`。
- 中文指令调用约：`capability.command` 命中后向模块传入 `{ 参数文本, 原文 }`：
  - `参数文本` 为命中指令后的剩余文本；`原文` 为完整指令，便于如 `r3d6` 这类“参数含在指令内”的命令。

### 4.5 权限模型

| 权限 | 含义 |
|---|---|
| `filesystem:read` | 读取指定位置的文件 |
| `filesystem:write` | 写入/删除文件 |
| `network` | 发起网络请求 |
| `exec` | 执行外部程序/脚本 |
| `device` | 访问设备（音频/摄像头等） |
| `clipboard` | 读写剪贴板 |

规则：
- 权限在能力声明与模块 manifest 两处声明，取交集生效；
- `危险` 或含 `exec`/`filesystem:write` 的能力默认不暴露给 MCP；
- 所有调用写入审计日志（来源、能力、参数摘要、结果、耗时）。

## 五、长任务（Job）

短请求用 `request/response`，广播用 `event`；**长任务不新增信封类型**，而是一组约定动作，
以保持协议兼容：

| 动作 | 语义 |
|---|---|
| `job.start` | 启动任务，返回 `{ jobId }`；参数含 `能力名`、`参数`、`工作目录`、`超时`、`环境变量` |
| `job.status` | 查询状态：`queued/running/done/failed/cancelled` + 进度 |
| `job.cancel` | 终止任务进程树 |
| `job.list` | 列出当前与历史任务 |
| `job.log`（event） | 流式推送 stdout/stderr 行 |
| `job.done`（event） | 完成事件，含退出码与产物路径 |

运行时要求：
- 独立进程、独立工作目录、显式环境变量；
- 超时与资源上限、可取消（Windows 终止进程树）；
- 历史落 SQLite（作业表），供 GUI 查看与重跑；
- 典型用途：Python 脚本、爬虫、安全测试、批处理。

## 六、模块与插件

### 6.1 三种模块形态

| 形态 | 实现 | 接入方式 |
|---|---|---|
| 内置模块 | TypeScript，`@kugua/*` 包 | 引用 SDK，作为 Nigane 客户端 |
| 脚本模块 | Python（或任意语言） | manifest + JSON-RPC over stdio |
| 外部项目 | 任意提供 MCP server 的程序 | 由 `@kugua/mcp` 客户端导入为能力 |

### 6.2 模块 manifest（`package.json` 的 `kugua` 字段）

每个模块包的 `package.json` 内用 `kugua` 字段声明其模块元信息（**单一事实来源**）：

```json
{
  "name": "@kugua/module-echo",
  "kugua": {
    "module": true,
    "type": "process",
    "entry": "dist/index.js",
    "autoStart": true,
    "description": "echo 示例模块（回声）"
  }
}
```

- `name` 默认取包目录名；`entry` 默认 `dist/index.js`；`type` 默认 `process`。
- `library` 类型用 `file` 指向产物（如 `bin/math.dll`），不随主控启动。
- `scripts/sync-modules.mjs` 扫描所有 workspace 包，据此自动生成 `kugua.config.json` 的 `modules[]`
  与根 `package.json` 中每个模块的 `start` 脚本；根 `build` 亦改为
  `npm run build --workspaces --if-present`（npm 按工作区依赖拓扑排序）。
- 因此**新增/删除模块只需建/删包并写 `kugua` 字段**，配置、启动脚本、构建顺序自动跟随；
  `npm run check:modules` 供 CI 校验一致性。

### 6.3 生命周期

`on_load` → `on_enable` → （运行）→ `on_disable` → `on_unload`；
运行时支持扫描、热重载、启用/停用、卸载。现有 `@kugua/plugin-sdk` 复用，增加能力声明。

#### 外部程序动态接入（苦音协议）

平台对外开放的接入面就是**主控的 WebSocket 端口**：任何语言、任何进程，
只要能用 WebSocket 收发 JSON，就能接入平台，成为与内置模块平级的模块。

- **协议规范**：`docs/接入协议.md`（成文规范，外部开发者据此实现）。
- **接入 SDK**：`sdk/` 目录，含 Python 单文件 SDK、完整示例与接入指南
  （`sdk/README.md`）。SDK 可直接复制到外部项目，不依赖本仓库。
  公开 API 全英文（`NiganeClient` / `register` / `on_event` / `request` /
  `broadcast` / `capability`），协议中文字段名由 SDK 内部封装。
- **参考实现**：`packages/nigane/src/index.ts` 的 `NiganeClient`。
- **最小示例**：`examples/external-module/run.mjs`，刻意不依赖本仓库任何包
  （只用 Node 内置能力 + 裸 WebSocket），证明协议可被复刻。
- **注册**：连接后 `hello` 握手即注册，进注册表与能力注册表，
  广播 `capability.changed`；其 `capabilityDefs` 的中文指令可直接出现在
  指令面板、可被 AI 路由、可进 GUI。
- **下线**：连接断开 → 主控 `unregistered` → 能力自动移除 → 广播刷新 UI。
  同名重连触发**顶号**，旧连接被替换。
- **与单例无关**：全局锁保证同一时刻只有一个平台在监听，
  所以外部程序不存在「连到错误的平台」的问题。

##### 两种生命周期（关键区别）

| 类型 | 平台退出/重启时 |
|---|---|
| 配置在 `kugua.config.json` 的 `modules[]`（托管） | 平台**负责关闭**：先 `SIGTERM`，2 秒未退强制 kill |
| 运行中接入的外部程序 | 平台**只广播 `system.shutdown`**，不发信号、不强杀，由对方自行决定是否退出 |

##### 关闭通道：为什么需要 `nigane.shutdown`

`system.shutdown` 必须在结束任何进程**之前**广播。但
**Windows 上对子进程 `kill("SIGTERM")` 实际是 `TerminateProcess` 硬杀**，
主控的 `process.on("SIGTERM")` 处理器不会执行，`关闭()` 不跑，广播就发不出去。

因此主控提供内置动作 `nigane.shutdown`（先回执、再异步优雅关闭），
WebUI 的 `重启平台()` 与 `/api/shutdown` 都改走 `请求主控关闭()` 调它，
仅在失败时回退到 `kill` 兜底。

**已知限制**：平台被强杀（任务管理器结束任务 / `kill -9` / 崩溃）时，
任何程序都无法拦截。推荐外部程序做兜底：连续重连 N 次失败后自行退出
（示例用 `KUGUA_RETRY_LIMIT`，默认 5）。

##### 托管式注册：外部程序自报「下次一起启动」

外部程序可在握手中上报 `托管` 字段，声明路径与启动参数：

```json
{ "name": "my-tool", "托管": { "enabled": true, "entry": "C:\\Python312\\python.exe", "args": ["main.py"], "cwd": "D:\\my-tool" } }
```

主控在 `registered` 事件里调 `处理托管申请()` 写入 `kugua.config.json`。

**冲突键 = 模块名**。不用物理路径做主键，因为路径会随目录迁移、
相对/绝对写法改变而变化，用它做主键会把同一模块当成新模块。
路径仅用于校验（不同模块名指向同一 `entry` → 警告 + 广播）。

**合并策略**：

| 场景 | 行为 |
|---|---|
| 模块名不存在 | 按上报新建配置并写盘 |
| 模块名已存在且一致 | 不变更 |
| 模块名已存在但有差异 | **保留用户配置**，记差异日志 + 广播 `registry.conflict` |
| 不同模块名指向同一 `entry` | 两者都保留，警告日志 + 广播 |

即：外部程序只能在**首次注册**时决定初始值，之后用户在管理界面改过的
配置**永不被外部覆盖**。这是避免「程序重启一次就把用户配置冲掉」的关键约束。

**管理面**：设置页「模块管理」+ 内置动作
`nigane.registry.config.list` / `nigane.registry.config.set`，
可逐项查看/编辑 **是否随平台启动**、**物理路径**、**启动参数**、说明。

**启动命令推断**：`启动模块()` 按 `entry` 扩展名选择启动方式 ——
`.js/.mjs/.cjs` 用 Node（沿用位置参数），`.py` 用 Python（`KUGUA_PYTHON` 可覆盖），
`.bat/.cmd` 用 `cmd /c`，其余直接执行。托管子进程额外注入
`KUGUA_URL`/`KUGUA_PORT`/`KUGUA_TOKEN`/`KUGUA_HOSTED=1`，
使非 Node 语言无需依赖位置参数约定。

##### 模块身份与版本门禁

外部模块不只上报能力，还上报**身份三要素**：`name`（主键）、`version`、`path`（本体物理路径）。
主控在**握手完成前**就做决策，不合规的接入不会进入注册表、不会污染能力表：

```
NiganeServer.握手校验(信息) → { 允许, 理由 }
        ↓
   校验接入()  ← packages/main/src/module-identity.ts 判定重新接入()
```

决策矩阵（实现在 `packages/main/src/module-identity.ts`，纯函数、可单测）：

| 原位 | 版本 | 信息变化 | 决策 |
|---|---|---|---|
| 是 | 更新 | — | `autoUpdate` ? **自动接受** : 放行并提示可手动更新 |
| 是 | 相同 | 有变化 | 暂下线 + 红灯 + `error`，手动「替换」 |
| 是 | 相同 | 无变化 | 正常上线 |
| 是 | 落后 | — | 暂下线 + `error`，手动「替换」（回滚） |
| 否 | — | — | **拒绝**，`warning`；只能先移除旧注册 |
| 无同名注册 | — | — | 首次注册放行 |

**为何要握手前拦截**：如果在 `registered` 事件后才判定，此时模块已完成注册，
能力已进能力表、其它模块已能路由到它；拒绝就变成「先上线再踢下线」，会留下一段
不可控时间窗。握手钩子保证「要么干净接入、要么根本不进表」。

**原位判定用自报 `path`，不用 `entry`**：托管启动时 `entry` 往往是解释器
（`python.exe`），模块本体才是 `main.py`；用 `entry` 比会把每次都判成非原位。
主控因此单独存 `modulePath` 字段。

**`module.query` 双向必需**：平台向模块发 `module.query` 获取当前身份；
模块未实现则无法校验版本，按离线处理（红灯）。为避免模块把协议动作当业务能力
暴露，平台在**首次上线后主动探测一次**并把结果写进配置的 `queryable` 字段，
后续门禁读该字段，不依赖模块自报能力列表。

**管理面**（设置页「模块管理」）：

| 控件 | 行为 |
|---|---|
| 刷新（蓝底 ↻） | 发 `nigane.registry.query` → `module.query`，超时即判离线 |
| 启用（滑动开关） | `autoStart`：下次启动平台时一并拉起；内置模块置灰固定开 |
| 自动更新（滑动开关） | `autoUpdate`；内置模块强制开且不可关 |
| 更新（绿底，旧→新） | 有新版本且无自动更新时出现；显式接受并重启模块 |
| 替换（黄底，旧→新） | 信息变化 / 版本回退时出现；按新信息重写注册 |
| 移除（红底 🗑） | `nigane.registry.remove`，先 `module.shutdown` 请求退出 |

「更新」与「替换」**互斥**，最多只出现一个（按上报情形选择）。

#### 运行时动态检测（模块）

主控不再只在启动时读一次配置：

- **`nigane.registry.reload`**：重读 `kugua.config.json`，与当前描述表做差集：
  新增模块写入描述表（process + autoStart 则拉起）、移除模块从描述表移除（先停其进程）、
  入口变化的模块重启以加载新代码；返回变更摘要并广播 `registry.changed`。
- **配置热检测**：每 5 秒比对配置文件指纹，变更后自动触发 `reload`，无需手动操作。

#### 运行时动态检测（插件）

`plugins` 模块监听插件目录（防抖）+ 15 秒定时兜底：
投放插件目录 → **自动发现并启用**；目录消失 → **自动卸载**；变更时广播 `plugins.changed`。
同时提供 `plugins.detect` 供手动触发；`install/update/reload/enable/disable/uninstall` 保持可用。

#### 单实例与端口冲突

- **全系统单例（强制）**：以**操作系统级锁文件**判定，由 `@kugua/paths` 的
  `抢占全局单例锁` / `读取单实例锁` / `全局单例锁路径` 提供。
  锁路径与 **cwd / 配置 / `KUGUA_DATA_DIR` 全部无关**：
  - Windows：`%LOCALAPPDATA%\KuguaStudio\studio.lock`
  - 其它：`$XDG_RUNTIME_DIR/kugua-studio/studio.lock`，回退 `~/.kugua-studio/studio.lock`
  - `KUGUA_GLOBAL_LOCK` 可显式覆盖（仅供测试隔离使用）

  因此**改端口、改配置、改数据目录、换目录启动都无法绕过**。
  用 `wx` 独占创建做**原子抢占**，两个进程同时启动也只有一个拿到锁；
  锁文件里记录持锁 pid，pid 已死或文件损坏视为陈旧锁自动接管；
  释放时校验 pid，只删自己的锁，绝不误删新实例的锁。
  发现已有实例时只提示并退出，**不发送任何信号、不结束任何进程**。
- **WebUI 与主控同属一个实例**：WebUI 先抢锁，再用 `KUGUA_LOCK_HELD=1`
  启动子主控；子主控校验锁确实存在且不属于自己后才跳过抢锁
  （避免环境变量被滥用绕过单例）。主控启动失败时 WebUI 一并退出并释放锁。
- **端口冲突 ≠ 已有实例**：端口可在配置中调整，也可能被其它程序占用。
  端口探测只用于报错——`启动失败：端口 <host>:<port> 已被其他程序占用，请修改 port`
  并以非 0 退出；**绝不把端口占用当作「已有 Studio 在运行」**。
  主控检查 `port`，WebUI 额外检查 `webui.port`。
- **退出钩子**：`process.on("exit")` 与优雅关闭都释放锁。
  被强杀（`TerminateProcess`）时不会触发钩子，但下次启动会因 pid 已死
  自动接管陈旧锁，不影响使用。
- **测试隔离**：`ui-gate.js` / `ui-check` 的隔离实例用
  `KUGUA_GLOBAL_LOCK=<临时目录>/studio.lock`，因此可与用户正在运行的 Studio 共存。
- **重启**：`POST /api/restart` 先关闭主控与全部模块，再 detached 重拉自身，
  旧进程释放锁后退出；设置页「平台运行」提供重启/退出按钮。

### 6.4 模块重写范式（阶段 1 落地）

后续功能模块统一按下式重写：**声明能力 + 处理函数**，不再各自实现入口与帮助文案。

```ts
import { NiganeClient } from "@kugua/nigane";
import type { 能力声明 } from "@kugua/capability";

// 1) 一处声明：指令 / GUI / 定时 / 外部接口均由注册表派生
const 能力清单: 能力声明[] = [
  {
    名称: "text.reverse",
    模块: "text",
    标题: "反转文本",
    说明: "将文本逐字反转",
    中文指令: ["反转"],
    参数: {
      type: "object",
      properties: { 文本: { type: "string", description: "待反转文本" } },
      required: ["文本"],
    },
    暴露: { 指令: true, GUI: true, 定时: false, MCP: false },
  },
];

// 2) 握手时上报能力声明；具体实现留在模块进程内
const 客户端 = new NiganeClient({
  name: "text",
  host, port, token,
  capabilities: 能力清单.map((c) => c.名称),
  // capabilityDefs: 能力清单   // 阶段 1 在 NiganeClient 选项中加入
});

客户端.onRequest("text.reverse", (参数) => {
  const { 文本 } = 参数 as { 文本: string };
  return [...文本].reverse().join("");
});

await 客户端.connect();
```

约定：
- 能力名与动作名使用英文 `模块.动作`；
- 参数一律用 JSON Schema 描述，便于 GUI 表单与 MCP inputSchema 复用；
- 需要文件/网络/执行权限的能力必须在 `权限` 中声明；
- 长任务（脚本/爬虫）声明 `长任务: true`，走 `job.*` 约定。

### 6.5 自带 UI 页（插件与模块通用）

> **三层 UI 表面**：
> | 需求 | 机制 | 表达能力 |
> |---|---|---|
> | 开关、地址、下拉 | 声明式表单（6.6） | 低 |
> | 实时数值、曲线、进度 | **小组件**（《小组件设计.md》） | 中 |
> | 音色试听、模型下载 | iframe 自定义页（本节） | 高 |
>
> 常见需求落在前两层，就不必碰 iframe。
>
> **小组件的职责分界**：插件只说「块里显示什么」和「哪个重要」（`prominence` /
> `group`），**不说放哪里、多大、什么形状**——那是 GUI 的自由。
> 因此布局字段永不进插件契约，GUI 改布局也就不需要插件配合。
>
> 实现位置：协议在 `nigane/widget-protocol.ts`，注册表与布局存储在
> `main/widgets.ts`，渲染在 `webui/renderer/parts/19-widgets.ts`，
> 限流在 `webui/widget-throttle.ts`。

插件与模块都可以声明一个自定义页，WebUI 会自动为其生成顶栏标签页。

**插件**在 manifest（`kugua-plugin.json`）中声明：

```json
{ "ui": { "title": "示例页", "entry": "ui/index.html" } }
```

**模块**在握手时上报（`entry` 相对模块入口文件所在目录）：

```ts
void 启动模块({ name: "tts", 界面: { title: "语音合成", entry: "ui/index.html" } });
```

两者共用同一套 iframe 机制与 `window.kugua` 桥，区别只在静态资源前缀
（`/plugin-ui/` vs `/module-ui/`）。

- **托管**：WebUI 服务提供 `GET /plugin-ui/<插件名>/<路径>` 与
  `GET /module-ui/<模块名>/<路径>`（默认取各自声明的 `entry`；防目录穿越，
  解析后必须仍在根目录内，否则 403）。
- **列表**：`GET /api/plugin-pages` 与 `GET /api/module-pages`。
- **模块根目录的确定**：模块可能在任何位置，平台只知道它的入口文件路径，
  因此约定 UI 目录**相对于入口文件所在目录**。
- **调用能力**：插件页引入 `/plugin-sdk.js` 后即得 `window.kugua`
  （`request` / `broadcast` / `getFileUrl` / `readMediaFile` / `dialog` 等，仅 HTTP、不建 WebSocket）。
- **隔离**：插件页在 iframe 中加载，与主界面隔离；示例见 `templates/plugin-template/ui/index.html`。

### 6.6 模块配置页（声明式，平台自动渲染）

模块**不需要写任何前端代码**就能得到配置界面：握手上报 `配置声明`，平台据此渲染表单。

```ts
const 声明: 配置声明 = {
  说明: "语音合成引擎配置。",
  字段: [
    { 键: "defaultEngine", 标题: "默认引擎", 类型: "select",
      选项: [{ 值: "voxcpm", 标题: "VoxCPM（快速）" }] },
    { 键: "engines.voxcpm.url", 标题: "服务地址", 类型: "string",
      提示: "http://127.0.0.1:9881" },
    { 键: "engines.voxcpm.apiKey", 标题: "访问密钥", 类型: "secret", 凭据: true },
  ],
};

void 启动模块({ name: "tts", 配置声明: 声明, 配置变更: (载荷) => 应用新配置(载荷.配置) });
```

#### 为什么用声明式而不是每个模块写 HTML

iframe 自定义页（6.5）表达力最强，但每个模块各写一套前端会导致风格分裂、
状态管理各说各话、第三方模块接入成本高。**绝大多数配置就是「几个开关 + 几个地址」**，
声明式表单覆盖这类需求成本几乎为零。

于是形成两层：

| 需求 | 方案 |
|---|---|
| 开关、地址、路径、下拉、列表 | **声明式表单**（本节），不写代码 |
| 音色试听、模型下载进度等复杂交互 | **iframe 自定义页**（6.5），按需提供 |

#### 字段类型

`string` / `text` / `number`（可限范围与步进）/ `boolean` / `select` / `path` / `secret` /
`array`（字符串列表或对象表格，含增删行）。

`键` 支持点号表达嵌套，如 `engines.voxcpm.url` ↔ `kugua.config.json` 里
`{ "tts": { "engines": { "voxcpm": { "url": … } } } }`。

#### 双向配置推送

配置不走轮询，走事件推送，和 `module.updateAvailable` 同一套路：

```
模块握手 ──上报 配置声明──▶ 平台
   ▲                           │
   │                     平台渲染表单
   │                           │
   │◀── module.config ──── 用户改配置（来源：用户）
   │      （完整配置）          │
   │◀── module.config ──── 模块刚上线（来源：初始化）
   │
   └── nigane.moduleConfig.report ──▶ 平台写盘 ──▶ 广播给所有模块（来源：模块）
```

- **平台 → 模块**：`module.config` 事件，载荷含**合并后的完整配置**、来源与变更键列表。
  模块收到后自行热重载，不必重启进程。
- **模块 → 平台**：`nigane.moduleConfig.report` 请求。模块可主动改自己的配置
  （例如自动发现到新音色后写入），平台写盘成功后**广播给所有模块**。
- **初始化推送**：模块每次上线都会收到一次 `来源: "初始化"` 的推送，
  因此模块不必自己读配置文件。

#### 三个约束

1. **凭据不落公共配置**。字段标 `凭据: true` 时，值写入 `kugua.config.local.json`
   （已 gitignore），公共配置里不出现；表单模型回传时**只给「已设置」标记，不给明文**。
2. **平台不理解字段含义**。平台只做存储、类型校验、凭据隔离——含义由模块自己解释。
3. **改配置失败就不落盘**。类型校验不通过时抛错，原文件不动。

#### 接口

| 接口 | 说明 |
|---|---|
| `nigane.moduleConfig.declarations` | 所有模块的配置声明（供 UI 判断哪些模块有配置页） |
| `nigane.moduleConfig.get` | 某模块的表单模型（值已合并、凭据脱敏） |
| `nigane.moduleConfig.set` | 写配置并推送（凭据自动分流到 local 文件） |
| `nigane.moduleConfig.report` | 模块主动上报配置变更，平台写盘后广播 |

#### 与插件的关系

模块与插件是**两种进程模型**，不合并：

| | 模块 | 插件 |
|---|---|---|
| 形态 | 独立进程，WebSocket 接入 | 同进程动态 import |
| 能做什么 | 声明能力，可被任意模块/MCP/定时调用 | 注册聊天正则命令 |
| 崩溃影响 | 只影响自己 | 拖垮主控 |

插件唯一不可替代的能力是**注册正则命令**（写 20 行就能加一条聊天命令）；
模块唯一不可替代的是**进程隔离与外部可调用**。两者共存。

配置页机制是按「扩展」概念统一设计的，插件后续也走同一套声明式表单，
用户侧不区分某个功能是模块还是插件。

#### 6.6.1 数组里的凭据（一个真实漏洞）

顶层字段的凭据隔离很好做：键名对得上就行。但**对象数组**才是容易出事的地方：

```json
{ "ai": { "providers": [
    { "name": "lmstudio", "baseUrl": "...", "apiKey": "sk-xxx" }
] } }
```

最初的实现只认顶层 `凭据: true`，于是表格里的 `apiKey` 会随
`providers` 一起写进 `kugua.config.json`——**被提交进版本库**。

修复的要点有三条，缺一条都不成立：

1. **列级声明**：`配置列声明.凭据`。没有它，平台不知道哪一列敏感。
2. **拆分时带上主键**：凭据层必须存成 `[{ apiKey, name }]` 而不是
   `[{ apiKey }]`。第一列视作主键。少了主键，读取时对不回行，
   密钥等于丢失（模块侧 `hasKey` 会一直是 `false`）。
3. **按主键合并而非按行号**：用户在配置页里删行、调序后，
   按位置合会把密钥配到错误的人身上。

读取顺序也有讲究：**公开层必须从主配置取**，不能从「深合并的结果」取。
数组是整体替换语义，合并后的数组其实已经是凭据层（里面没有 name/baseUrl），
拿它当公开层会把公开字段全丢掉。

#### 6.6.2 模块读取配置时也要合并两层

平台把凭据写进 local 文件，但模块自己读配置时也必须合并两层，
否则会出现「配置页里填了密钥、模块却说没有密钥」的诡异现象。

AI 模块的 provider 列表是 `合并提供方(主, 覆盖)`：**按名称逐行补 apiKey**，
其余字段以主配置为准。不能整表覆盖——local 文件里只有 apiKey 一列。

### 6.7 插件与平台同进程：取舍与保护

插件**不做进程隔离**，这是有意的选择：

- 插件面向的是「常用功能」（正则命令、快捷回复），每条聊天消息都要过一遍；
  跨进程 RPC 会把微秒级的正则匹配变成一次往返
- 生命周期完全由平台掌控：加载/卸载/热重载都是同进程操作，没有僵尸进程问题

代价很明确：**插件的错误就是平台的错误**。所以补了三层保护：

| 保护 | 解决什么 | 位置 |
|---|---|---|
| 进程兜底 | 定时器/事件回调抛错、未处理拒绝 → 直接杀主控 | `module-kit/process-guard.ts` |
| 命令超时 | 卡住的命令永久占住分发流程 | `plugins/loader.ts` `限时()` |
| handler 超时 | 一端永久等待导致连接资源不释放 | `nigane` 服务端/客户端 |

**能力边界要说清楚**：超时不能中断已经在执行的同步死循环（JS 无法从外部
杀掉一个正在跑的函数），它只保证「分发流程不再等待」。如果将来确实需要
防恶意插件，再引入隔离，但不能以牺牲常用路径的效率为代价。

### 6.8 扩展统一列表

设置里「模块管理」与「插件管理」是分项管理界面；但用户找功能时不该先想
「这功能是模块还是插件」。因此插件页顶部有一个**全部扩展**列表，把两者合表展示：

- 统一的「模块」/「插件」徽章区分来源
- 统一的在线状态点与状态文案
- 上报了配置声明的模块多一个「可配置」标记
- 一个搜索框按名称、说明、能力/命令过滤

这只是**视图层的合并**，两类东西的语义、生命周期、调用路径完全不变。
排序规则：在线优先 → 模块优先 → 名称。

## 六·五、WebUI 前端结构

- **入口**：`packages/webui`（HTTP + WebSocket + 静态页）；浏览器通过 `kugua-shim.js` 注入
  与旧 Electron 一致的 `window.kugua`，渲染层直接复用。
- **桥接层（TS + ESM）**：`src/renderer/bridge.ts` 是 `window.kugua` 的**唯一类型与实现来源**
  （`苦瓜基础接口` / `苦瓜接口` + `请求()` + `创建基础接口()`）；
  `kugua-shim.ts`（主界面，含 WebSocket 日志/就绪/总线事件订阅与窗口控制占位）与 `plugin-sdk.ts`
  （插件页，仅 HTTP、无窗口控制）均由其派生；`01-types.ts` 的 `Window.kugua` 直接引用 `bridge` 类型。
- **前端刷新策略（事件驱动）**：主控广播的总线事件（`registry.changed` / `capability.changed` /
  `plugins.changed`）由 WebUI 服务端转发到浏览器（WS `{ type: "bus", action, params }`），

  | `13-tools.ts` | 工具页（音乐/媒体/模式/二维码） |
  | `14-plugin-ui.ts` | 插件自带 UI 页（iframe + plugin-sdk） |
  | `15-misc.ts` | 主题、侧栏、拖拽、预览交互、文本编辑器 |
  | `16-cmd-panel.ts` | 聊天页左侧「指令面板」（注册表驱动、最近使用、单击调用/填前缀、双击持续前缀） |

  构建：`tsc -p tsconfig.renderer.json` 仅做类型检查（`module: ESNext` + `moduleResolution: Bundler`，`noEmit`），
  再由 `scripts/build-renderer.mjs`（esbuild）产出**三个 IIFE 产物**：`index.js`（主界面）、
  `kugua-shim.js`（桥接，必须早于 index.js 加载）、`plugin-sdk.js`（经 `/plugin-sdk.js` 给插件页）。
  约束：ESM 下**导入绑定不可写**，共享可变状态需在拥有模块内提供 setter（如
  `设置提示选中索引` / `设置图片缩放倍率`）或改为对象属性；`Window` 增强需写在 `declare global { ... }` 中。
  例外：命名空间成员（如 `Explorer.标签树` / `Explorer.选中内容`）是**对象属性**，跨模块可读可写，
  因此子模块与核心之间直接以 `Explorer.成员` 共享状态，无需 setter。
- **`init` 只做编排**：`Explorer.init()` 仅按序调用 `绑定搜索与视图事件` / `绑定智能视图与位置事件` /
  `绑定内容操作事件` / `绑定详情标签事件` / `绑定编辑器事件` / `绑定对话框事件` / `绑定页面切换事件` /
  `绑定容器交互事件`，随后加载数据并 `切换视图`；具体 DOM 绑定在各命名函数内。
- **页面/标签**：统一在 `视图映射` 注册（对话 / 知识库 / 作业 / 工具 / 插件 / 日志 / 设置），
  新增页面只需登记一条映射 + 一个按钮，入口一致且互不耦合。
- **对话页**：多对话/多项目（localStorage 持久化）。**指令面板**（`16-cmd-panel.ts`，聊天页左侧）
  从能力注册表（`capability.list`）+ 本地路由内置指令库 + **路由前缀表**（`04-router.ts` 的
  `指令前缀表` / `推断指令需参`）汇总，并随 `capability.changed` 刷新；
  **单击**免参指令直接调用、需参指令（如 `吃什么` / `谐音`）只把前缀填入输入框；
  **双击**设为互斥的**持续前缀（对话模式）**，此后每条输入自动拼接该前缀
  （`08-logs.ts` 发送前由 `应用持续前缀` 处理）。**最近使用**排最前
  （localStorage `kugua_recent_cmds_v1`）；可筛选、拖拽调宽、折叠。
- **随机汉字**：指令 `随机n*m`（对齐参考 C# `handleRandomString`）——**n = 列、m = 行**，
  如 `随机5*4` → 5 字一行共 4 行；行/列默认 1，总量 > 2500 时自适应截断。
- **渲染层依赖方向（禁止成环）**：`07-explorer.ts` **不得**依赖 `08-logs.ts`，
  且 `Explorer.init()` **只能**在 `09-init.ts` 调用。历史原因是两者互相 import，
  esbuild 打包后 `onReady` 里拿到的 `Explorer` 绑定尚未就绪，会抛
  `Cannot read properties of undefined (reading 'init')`，导致知识库列表不渲染、
  编辑器事件不绑定。该约束已由 `cmd-panel.test.ts` 的「模块依赖」用例守住。
- **内置文本编辑器**：`.editor-toolbar`（文件名 / 查找 / 换行 / 字号 / 保存）
  + `.editor-gutter`（行号，滚动同步）+ 编辑区 + `.editor-statusbar`
  （`行 n, 列 m` / 字符数 / 行数 / 脏标记）。快捷键：`Ctrl+S` 保存、`Ctrl+F` 查找、
  `Tab`/`Shift+Tab` 缩进与反缩进、`Enter` 保持缩进、`Ctrl+滚轮` 缩放字号；
  字号与换行偏好存 `localStorage`（`kugua_editor_font` / `kugua_editor_wrap`）。
- **保存语义（改谁）**：保存走 `mkg.file.write` → 资源物理路径。
  拖入/导入的文件经 `importFile` 复制到库目录，改的是**副本**；
  「位置」扫描进来的是**原址索引**，保存会**直接修改原始文件**。
  故保存前用 `mkg.file.pathInfo` 取 `inPlace`，原址文件弹确认框
  `这将直接修改原始文件：<路径>`。保存后**无条件**刷新内容列表与信息面板
  （此前只在片段时刷新，导致文件保存后列表仍显示旧 size/修改时间）。
- **消息就地编辑 / 回复版本**：回复统一收进用户气泡下的 `.msg-replies` 容器；
  每次执行生成一个版本，历史存 `data-versions`（随对话 `innerHTML` 持久化）。
  点击自己发的消息可就地编辑（Enter 提交 / Esc 取消），重发**不新增 user 气泡**，
  结果作为新版本追加；多版本时容器左下角显示 `‹ n/N ›` 导航条可左右回切。
  为避免重发把整个历史发给 AI，编辑后重发只重跑该条指令（`处理输入重发`）。
- **回复栏图标**（模块名右侧同一行）：`▾ 折叠` / `↻ 刷新` / `☆ 收藏`。
  折叠只留模块名一行；刷新 = 重跑原指令作为新版本；
  收藏写入知识库——文本 → `mkg.note.create` 笔记，多媒体（`data:` 图片/音频）
  → `mkg.resource.saveBase64` 资源文件 + 笔记引用；
  标签 = 模块名 + 当前对话标题。已收藏显示左侧 ★ 与黄色强调条，再点取消。
- **输入路由**：**指令优先**——先走本地路由（`路由指令`），再走能力注册表（`capability.command`）；
  均未命中则提示「未识别的指令」，**不再兑底发给 AI**。AI 对话需显式前缀 `ai <内容>`（忽略大小写，
  兼容 `问AI` / `AI问答`），并委托带会话记忆的 `与AI对话`（按 `chatId` 保留上下文）。
- **日志页**：**分标签**——通信日志（总线收发，前端缓存）与系统日志（`nigane log.tail`，含各模块/插件细节与报错）各占一个标签，
  标签上带条数徽标；系统日志支持 调试/信息/警告/错误 四级筛选（调试默认收起）。
  - **为什么分标签**：两者是两种东西（“发了什么” vs “内部怎么想”），上下堆叠时各占 42vh，
    两边同时在实时滚动根本盯不过来，大屏还浪费一半高度。
  - **通信日志不记 ping/pong 与 `widget.data`**：两者周期性且量极大，会把 1000 条环形缓冲冲光，
    出问题时反而翻不到出事前的上下文。`params`/`data` 超过 8000 字符只存开头 + 大小说明，
    避免大 payload（base64/大 JSON）把内存撑到几百 MB。
- **插件 UI**：插件 manifest 声明 `ui` 即自动生成标签页（iframe + `/plugin-sdk.js`）。
- **常驻**：Windows 系统托盘（`packages/webui/tray.ps1`，PowerShell NotifyIcon）：左键打开 WebUI，
  右键菜单「打开 / 开机启动（勾选，联动登录计划任务）/ 退出（终止服务进程树）」；
  带看门狗（服务退出则托盘自动退出）；`webui.tray=false` 关闭。
  实现约束：**不要用 `detached: true` 启动 powershell**（Windows 下会立即以 0 退出且不执行），
  改用 `windowsHide: true` + `unref()`，日志写入 `<数据目录>/tray.log`。
- **回归验证（已接入 npm 门禁）**：`npm run test:ui`（= webui 构建 + `scripts/ui-gate.mjs`）自动启服务、
  用无头 Chrome（CDP）断言：标签/视图齐全、切页无异常、系统日志渲染（`log.tail`）、新建对话（localStorage）、
  指令提示、主题切换、AI 模型列表，以及知识库的**写入回归**（新建点子/素材/记事列/卡片、新建片段并打开内置编辑器），

- **知识库信息架构（重构后）**：统一为三个子标签 `.ex-sub-tabs`：

## 六·六、AI 接入（统一网关）

AI 不是平台依赖，而是一项可选能力，统一由 `ai` 模块暴露。

### 提供方两层

1. **普通 OpenAI 兼容端点**（`ai.providers[]`）：LM Studio / Ollama / 各云厂商；
   每个提供方配 `baseUrl` + `apiKey` + `models{chat,image,embed}`，
   未指定模型时自动取 `/models` 的第一个。
2. **OpenWebUI 网关**（`ai.openwebui`）：把 OpenWebUI 当作「模型目录」。
   它内部已经接了几十个上游连接，自己在管理页加减模型；
   平台只需认它一个端点，就能拿到全部模型。

### 为什么 OpenWebUI 要单独实现

它虽然提供 OpenAI 兼容路径，但有四个实质差异，塞进通用 `client.ts` 会互相干扰：

| 差异 | 影响 |
|---|---|
| 鉴权是**登录态 JWT**（会过期） | 需要自动登录取 token、缓存至 `data/ai/openwebui-token.json`，临近过期自动续期 |
| 模型 id 带**连接前缀**（`硅基流动.Qwen/Qwen3-8B`） | 需要拆解 `prefix` / `name`，UI 按连接分组 |
| 对话走 `/api/chat/completions` 而非 `/v1/...` | 路径不同 |
| 错误体**非标准**（`{code,message}` 或嵌套 `{error:{message}}`） | 必须提取人话，否则用户只看到「HTTP 402」 |

### 模型路由规则

`ai.chat` 按以下优先级选通路：

1. `provider === "openwebui"` → 强制走 OpenWebUI
2. `model` 形如 `前缀.模型名` 且已启用 OpenWebUI → 自动走 OpenWebUI
3. 只配了 OpenWebUI（无普通提供方）→ 走 OpenWebUI
4. 否则 → 走配置里的普通提供方

这样调用方无需关心后端是谁，直接用模型 id 即可。

### 凭据不落仓库

配置支持两层合并：

```
kugua.config.json          ← 入库，只放 baseUrl / email / defaultModel
kugua.config.local.json    ← 不入库（.gitignore），只放 password / token
```

读取时后者覆盖前者（空串视为未设置，回落前者）。也支持环境变量
`KUGUA_OPENWEBUI_URL` / `_EMAIL` / `_PASSWORD` / `_TOKEN` / `_MODEL`。

### 界面

对话页头部的模型下拉按「连接」分组列出全部模型（几百个也很顺），
悬停提示显示连通性与模型总数，旁边的 ↻ 按钮强制刷新缓存（默认 60 秒）。

### 一个必须小心的坑

主控每次落盘（模块上下线、托管注册等）都会重写整份配置。
早期实现只挑出自己认识的字段再写回，导致 `ai` / `plugins` 这类
**模块自己的配置节被静默抹掉**。现在 `加载配置()` 先展开原文件，
再覆盖自己认识的字段，保证不认识的节原样透传。

## 六·七、两种 UI 端：浏览器 WebUI 与 Tauri 桌面壳

同一套渲染层、同一套服务端，两种装载方式：

| | 浏览器 WebUI | Tauri 桌面壳 |
|---|---|---|
| 入口 | `start.bat` → 默认浏览器 | `packages/desktop` 可执行文件 |
| 渲染引擎 | 用户装的 Chrome/Edge | **系统 WebView2**（Edge 内核） |
| 受浏览器影响 | 是 | **否**（独立的 WebView2 进程树） |
| 窗口控制 | 按钮隐藏 | 原生最小化/最大化/关闭 |
| 安装体积 | 0 | ~5–10MB（不打包浏览器） |

### 六·七·一、单例与 GUI 模式选择

**窗口为什么会越开越多**

`start.bat` 每次运行都会启动桌面壳。原来的桌面壳没有单例检查，所以点几次就有
几个窗口——而且它们都指向同一个后端，看起来像「打开了多份 Studio」，
实际是同一份数据被多个窗口同时操作（"这边改了那边没变"的经典来源）。

现在桌面壳启动时**第一件事**就是取一个具名互斥体
（`Local\KuguaStudio.DesktopShell`）：

- 拿到了 → 本进程是唯一实例，正常启动
- 没拿到 → 已有窗口在运行，**把那个窗口唤到前台**（最小化则先还原）然后退出

选互斥体而不是锁文件，是因为互斥体是内核对象：进程一死（含被任务管理器强杀）
系统自动释放，不会留下残留锁导致「再也打不开」。

检查放在所有初始化之前，否则会看到「新窗口闪一下才退出」。

**选哪种 GUI**

`kugua.config.json`：

```json
{ "webui": { "gui": "desktop" } }
```

| 值 | 行为 |
|---|---|
| `desktop` | 启动 Tauri 桌面壳（独立窗口，不依赖浏览器） |
| `browser` | 用默认浏览器打开 WebUI |
| 不写 | 桌面壳已构建则 `desktop`，否则 `browser` |

临时覆盖不改配置：`set KUGUA_GUI=browser`。

浏览器模式下 `start.bat` 会**先探测端口**：已经在跑就直接打开 URL 复用，
不再起第二个后端进程。

### 六·七·二、前端断线提示

WebSocket 断开后页面**看起来还是好的**——按钮能点、输入框能打字，
但所有请求都会失败。用户分不清是「后台挂了」还是「这个功能坏了」，
只会反复点、反复失败，最后以为程序坏了。

所以断线必须让用户看见：`kugua-shim.ts` 在 `onclose` 时显示顶部横幅
（含重连次数与处置建议），收到 `ready` 自动隐藏。横幅出现时页面整体下推
30px，不遮挡顶部工具栏。

**光提示不够，还要停发请求。** 日志与总线走 WebSocket，但所有
`window.kugua.request` 走的是 `/api/request`（HTTP），**两者完全独立**——
WS 断了 HTTP 不受影响，请求还是一个个发出去，在各自超时里逐个失败。
所以 `bridge.ts` 里有个全局闸门 `设置后台连通()`：断线关闸，
请求立刻返回明确错误（1ms，此前要等 10 秒超时）；重连开闸。

**重连后不自动重载。** 断线期间后台可能变了很多，界面还是旧数据；
自动重载会丢掉用户正在写的内容。折中做法是重连成功后显示黄色提示
「已重新连接。断线期间后台数据可能已变化，点击此处刷新页面。」，
点一下即重载。这条提示**不自动消失**——数据过期的风险在用户刷新之前
一直存在，自动收起会让他误以为没事了。

### 六·七·二附、`/api/request` 的错误表达

同一个接口要同时表达两类失败，早期没分清，代价不小：

| 类型 | 例子 | 怎么表达 |
|---|---|---|
| **传输层故障** | 路由不存在、读体失败、服务内部异常 | HTTP 5xx + `{ error }` |
| **业务拒绝** | 模块未启动、没配 OpenWebUI、下游报错 | HTTP **200** + `{ __kuguaError }` |

为什么不能都用 5xx：**浏览器会把每一个非 2xx 响应都记成控制台错误**。
而「没配 OpenWebUI」是**正常状态**——结果是用户一打开 AI 页就满屏红字，
真正的问题反而看不见；UI 门禁也因为「控制台必须干净」这条硬规则一直判失败。
同理也不能用 `{ ok: false }`：业务结果里 `ok` 太常见，会误判。

客户端（`bridge.ts` 的 `请求()`）对两种情况**行为一致**：都抛 `Error`，
错误文本就是平台的原话、不加包装（调用方常直接展示给用户）。
这条不能松——把错误吞掉比报 500 更糟。
### 六·七·三附、启动 / 退出 / 重启的健壮性

这块是平台的稳定性基础，但**出问题时最难查**：平台看起来好好的，
其实是空壳；或者重启一次就彻底没了。下面每一条都对应一次真实故障。

**一、一切路径都不能依赖 cwd。**

WebUI 用 `process.cwd()` 拼主控路径，从子目录启动就得到
`packages/packages/main/dist/index.js`——主控根本没起来。更糟的是它只打
一行警告就继续：用户得到一个能打开的界面，所有按钮都失败，而且
**全局锁已经被它抢走了**，正常启动反而被告知「已有实例在运行」。

现在 WebUI 和主控都以**自身文件位置**为准：

| 组件 | 怎么定位仓库根 |
|---|---|
| WebUI `dist/server.js` | `resolve(__dirname, "..", "..", "..")` |
| 主控 `dist/index.js` | `import.meta.url` → `dirname` → 上溯三级，然后 `process.chdir` |

主控里到处是 `process.cwd()`（配置、模块入口、库文件、data 目录），
与其改几十处，不如**启动时把 cwd 归一化到仓库根**，一处解决。

两个必须注意的细节：

- **ESM 里没有 `__dirname`**。用了会抛 `ReferenceError`，而它一旦被
  `catch {}` 吞掉，整个归一化就**静默失效**——这次真的踩了。
  所有失败分支都要能看见，静默失败比崩溃更难查。
- `KUGUA_CONFIG` / `KUGUA_CONFIG_LOCAL` 若给的是**相对路径**，必须先按
  调用者原本的 cwd 解析成绝对路径，再 chdir。否则指向变了，那是改写用户意图。

  还有一个更容易踩的：**环境变量必须真的被读**。`本地配置路径()` 曾经硬编码
  `cwd/kugua.config.local.json`，不看 `KUGUA_CONFIG_LOCAL`——设了也不生效，
  主控照样去读 cwd 下那个文件（多半不存在），凭据层整层静默丢失，
  界面上只显示「未配置」。隔离测试、多实例、便携模式全都受影响。
  两个配置路径必须走同一套解析方式，不能一边认环境变量一边不认。

### 六·七·七、外部工具：进程启动次数是主要成本，不是单次耗时

图片模块要频繁调 `magick.exe`，重构前先实测了一轮，结论反直觉：

- **单次启动固定 ~65ms**（Windows）。看起来不多，但乘上次数就不一样了。
- **base64 + JSON 传输几乎免费**：3.2MB 的图编码加序列化只要 **4ms**。
  之前打算做路径契约「省 CPU」是判断错了——要省的是**体积**
  （30 帧 base64 是 3.7MB，路径只有 1.4KB，差 2687 倍），不是延迟。
- **真正的浪费是「一件事拆成 N 个进程」**。`做旧单帧` 原来把 JPEG 往返
  循环写成每轮两个进程（转 JPEG 一个、转回 PNG 一个），35 轮就是 70 次
  启动，600x400 实测 **6.6 秒**。改成一条命令里用 `-write` / `+delete` /
  `-read` 串联，**1.9 秒**，像素逐字节一致。

两条可复用的经验：

1. **凡「循环里调外部进程」，先问能不能塞进一条命令**。ImageMagick 支持
   多输出（`frame-%03d.png`）和命令内中转（`-write` / `-read`），
   一次调用能干完的事不要拆成 N 次。
2. **合并时优先用临时文件而不是管道**。stdin 是一次性的，第一轮读完就空，
   第二轮 `-read` 会报 `insufficient image data`。

但也有不该合并的：`upscale` 的逐帧路径试过用 `-coalesce` 一次处理整个
GIF 序列，20 帧只快 1.4 倍——`-coalesce` 要先解压全部帧，把启动开销的
节省吃掉了。**收益不够抵代码复杂度就不改**。

还有一条：**别为了省体积牺牲正确性**。拆出来的帧用 JPEG 存能小 2.1 倍，
但 GIF 帧可能带透明通道，存 JPEG 会丢。这种"优化"不做。

### 六·七·八、测试里取端口不能用 `listen(0)`

三个集成测试文件原来都是「绑 0 端口、读回端口号、`close()`、交给子进程」。
这有两个洞：

1. **Windows 保留段**：绑 0 拿到的是动态段（49152–65535），而
   Hyper-V / WinNAT 会保留其中若干段。落进保留段不是"被占用"，是
   "根本不让绑"——直接 `EACCES`。全量跑时偶发，单跑必过。
2. **竞态**：`close()` 到子进程真正 listen 之间，端口可能被别人抢走。

现在每个测试文件用自己的固定段（`packages/webui/test/port-pool.ts`
登记），段内**递增探测**。

递增这一点不能省：同一文件要「主控 + WebUI」两个端口，每次都从基数
开始扫会返回同一个值，两个子进程抢同一端口——表现为启动超时，看着
像被测代码坏了。

**二、半启动比不启动更糟。**

主控起不来时，WebUI 原来照常对外服务。用户看到完整界面、点什么都失败，
而锁被占着，再启动一次也进不来——彻底卡死。
现在 `启动主控()` 返回布尔值，没起来就**释放锁并 exit(1)**，日志说清
常见原因（未构建 / 主控端口被占）。

**三、重启不能把平台弄丢。**

`/api/restart` 的顺序是：spawn 新实例 → 释放锁 → exit。
新实例若抢在旧实例退出前跑到单实例守卫，会看到「旧实例还活着」而**自己退出**。
慢机器上这个窗口期是真实存在的。

所以重启出来的实例带 `KUGUA_RESTART_TAKEOVER=1`，允许**最多等 10 秒**锁。
等待期过了仍然放弃——设个环境变量不能变成开第二个实例的后门
（有测试专门守这条）。

**四、退出时不能留下孤儿进程。**

进程树是三层：主控 → 模块 → 模块自己 spawn 的命令（`job` 跑任务、
`scheduler` 跑计划任务）。Windows 上 `child.kill("SIGTERM")` **只杀直接子进程**，
孙进程会残留。

目前的实际防线：

| 场景 | 靠什么收尾 |
|---|---|
| 正常退出 | 广播 `system.shutdown` → 主控逐个 SIGTERM → 2 秒后 SIGKILL 兜底 |
| 主控被强杀 | 模块收到 WebSocket `close` 事件后自己退出，连带收掉孙进程 |
| 桌面壳异常死亡 | Windows Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）由系统连根收走 |

实测三层进程树在「强杀主控」后 2 秒内清空。**注意这套防线依赖 WebSocket
能感知 TCP 断开**；主控卡死（进程活着但不再应答）是唯一没有覆盖的情况。

**五、模块崩溃不自动重启。**

托管模式下模块 `close` 即退出（重连反而更脆弱：状态可能对不上），
由主控重新拉起。但**运行期**崩溃不自动重启——避免一个启动即崩的模块
把主控拖进无限重启循环。代价是崩溃后模块永久离线，需要手动干预。
所以这种情况的日志级别是 `warn` 而不是 `info`，并在正文里写明
「已离线，需要手动重启」。

**六、开机启动的端口必须走命令行。**

计划任务的 `-Port` 参数原来写成 `$env:KUGUA_WEBUI_PORT = "$Port"`，
那只影响**安装脚本自己的进程**，进不了任务定义——参数装了也白装，
任务永远读配置里的端口。现在作为 `--port N` 写进任务命令行，
`schtasks /Query` 里直接看得见。

**七、`chcp 65001` 要还回去。**

中文 Windows 控制台默认代码页 936（GBK），而平台全链路是 UTF-8，
不切就是乱码。但 `chcp` 是**进程级副作用**，`setlocal` 不会回滚它——
切完不还，用户自己的 cmd 窗口就一直是 UTF-8 了。
`start.bat` 开头记下 `OLDCP`，所有出口（成功 / 失败 / 未知 GUI 模式）
统一走 `:done_restore` 还原。

顺带一个批处理坑：`endlocal & exit /b %RC%` 里 `%RC%` 在 `endlocal`
之后**已失效**，必须用延迟展开 `!RC!`。

这些行为都由 `packages/webui/test/startup-robustness.test.ts` 守着（8 条），
且每一条都做过**反向验证**：临时把修复撤掉，测试必须失败——
否则就是假阳性，等于没测。
**八、WebUI 也有 6 处 cwd 依赖（同样是静默降级）。**

主控改完才想起来 WebUI 自己也一样。它比主控更阴险——**失败大多不报错**：

| 用途 | 从子目录启动的后果 |
|---|---|
| 配置文件 | 找不到 → 用默认配置，端口和 token 全是错的 |
| 插件目录 | 插件"全部消失" |
| 模块 UI 目录 | 模块自定义页打不开 |
| 桌面端 exe | 找不到 → 静默回落浏览器模式 |
| 数据目录 | 数据写到错误位置 |
| 托盘 `-Root` | 托盘脚本找不到，托盘不出现 |

已全部改为 `仓库根`（`__dirname` 上溯三级）。

**唯一保留 cwd 的地方**是 `KUGUA_CONFIG` 给相对路径时——那必须按**调用者**
的 cwd 解析，因为那是用户写下路径时的意思。主控那边因为要 `chdir`，
所以先把相对路径转成绝对路径再切目录，顺序不能反。

**九、`KUGUA_DATA_DIR` 没有贯到底。**

审计库和日志文件原来固定写 `<cwd>/data/`，**绕过了 `数据根()`**。
意思是设了 `KUGUA_DATA_DIR` 的实例（测试、便携版、多开调试）数据目录
已经改到别处，审计和日志却还往仓库里写——多个实例混进同一个库，
所谓"隔离运行"根本没隔离。现在统一走 `数据根()`。

顺带说个反过来的教训：**加固不等于修 bug**。我还给 `启动模块` 加了
防重复（同名模块已存在就先收掉旧的），但撤掉它实测**并不会产生孤儿**——
重名时第一个进程占住端口，第二个连不上会自己退出（模块自带 close 自退）。
所以这层只是把"靠模块自己退"变成"主控主动收"，顺带给出可见警告，
不应当成修了个严重问题来写。

**十、`proc.killed` 不是「进程死了」，它只是「调用过 kill」。**

关闭流程是：广播 → 逐个发 SIGTERM → 等 2 秒 → 对**还活着**的发 SIGKILL。
但判断条件原来写的是 `if (!记录.proc.killed)`，而 `killed` 在调用 `kill()`
后**立刻变 true**，跟进程有没有真的退出毫无关系。上一步刚发过 SIGTERM，
所以兜底整段被跳过——**等于没有兜底**。

实测确认：

```
运行中:     exitCode=null signalCode=null      killed=false
刚 kill 完: exitCode=null signalCode=null      killed=true   ← 旧判据已失效
确认退出后: exitCode=null signalCode=SIGKILL   killed=true
```

注意第三行：被 SIGKILL 之后 **`exitCode` 仍然是 null**，只有 `signalCode`
有值。所以正确判据必须两个都看：

```ts
记录.proc.exitCode === null && 记录.proc.signalCode === null  // 还活着
```

Windows 上 SIGTERM 被 Node 直接映射成硬杀，所以平时看不出这个 bug；
Linux/macOS 上 SIGTERM 可以被忽略，模块一卡住就会带着它退出。

**十一、托盘的「退出」不能强杀。**

设置页「退出平台」走 `/api/shutdown` → `关闭平台()` → 主控 `nigane.shutdown`
→ 广播 `system.shutdown`。而托盘右键「退出」原来是
`Stop-Process -Id $ServerPid -Force`，**直接硬杀**。

同一个动作两个结果，而且后果不对称：托管模块被强杀会自己退（靠 WebSocket
`close`），所以表面看没事——但**运行中接入的外部程序不受平台托管**，
它只能靠 `system.shutdown` 这条消息决定要不要退，收不到就成了没人管的
僵尸进程。审计和日志也来不及落盘。

现在托盘先 `POST /api/shutdown`，等最多 10 秒让主控自己退，仍在才回落强杀
（用 `Stop-Process` 而不是 `taskkill /F`，杀软规则更温和）。

对照实验（同一套外部程序接入脚本）：

| 退出方式 | 外部程序收到 `system.shutdown` |
|---|---|
| `POST /api/shutdown`（现在） | ✅ 收到 |
| `SIGKILL` 强杀（原来托盘） | ❌ 收不到 |

**十二、协议里有 ping/pong，但两端谁都没主动发过。**

`NiganeServer` 能回 `pong`，`信封` 类型里也定义了 `ping`/`pong`，
**但没有一处代码主动发 `ping`**——机制等于没实现，只占了个类型位。

这留下的空白正好是最难查的一类故障：**主控卡死**。进程还在、WebSocket
连接不断，但事件循环被阻塞、不再处理任何消息。此时：

- 模块那边 `close` 永远不触发 → 它以为自己一切正常，原地不动
- 平台变成「按钮点了没反应」的空壳，而且**永不自愈**
- 只有主动发请求时才 10 秒超时 → 用户以为单个功能坏了

实测（假主控握手成功后阻塞事件循环）：

```
主控卡死 4 秒后，模块连接是否断开: ❌ 没断开（模块以为一切正常）
请求结果: 请求超时（1005）→ 请求会失败，但连接本身没断
```

**必须双向**，这是容易只做一半的地方：

| 方向 | 能发现什么 | 只做这一边会怎样 |
|---|---|---|
| 主控 → 模块 | 模块进程卡死 | 主控卡死时，它自己发不出 ping |
| 模块 → 主控 | 主控卡死 | 主控不响应时，没人告诉模块 |

所以两边都发：主控每 30 秒 ping 一轮，上一轮标记还是 `false` 就 `terminate()`；
客户端同样每 30 秒 ping，一个周期内没等到 `pong` 就 `emit("heartbeat_timeout")` 并断开。

**不用 WebSocket 协议层的 ping 帧**：那是 TCP 层探测，由 `ws` 库自己回 pong，
只能测出连接断没断，恰恰测不出「进程活着但事件循环卡死」——而那正是要抓的情况。
所以走应用层消息（协议本来就定义了）。

最坏 2 个周期（约 60 秒）才发现，比「永远发现不了」好得多。定时器都 `unref()`，
并在 `stop()` / `close` 里清掉——否则进程退不掉，还会在关闭途中误判所有模块失联。

**十三、一个带裸 `%` 的请求就能打崩整个 WebUI。**

这一条原本在待办里记成「返回 500」，实测**严重得多**：进程直接 `exit code=1`。

```
GET /a%b  →  连接错误: fetch failed
进程是否还活着: 已退出 code=1
输出: URIError: URI malformed
```

根因是 `decodeURIComponent` 遇裸 `%`（或截断的 `%E4`）会抛 `URIError`，
而这个异常抛在 `createServer` 的回调里——**那里没人接**，Node 的默认行为是
让进程退出。也就是说：**一个不需要认证的请求就能把平台打掉**。

请求方甚至不需要恶意：旧书签、截断的分享链接、剪贴板里半截的中文链接，
都会变成裸 `%`。

同一个回调里还有第二处同类隐患：`new URL(req.url, `http://${host}`)` 遇到
畸形 Host 头（`"abc def"`、`"[["`、`"::::"`、空串）会抛 `TypeError`，
抛点一模一样。而 Host 头伪装成本极低。

修法两条，缺一不可：

1. `安全解码路径()`：解码失败退回**原始路径**。它已经过 `new URL()` 处理，
   不会抛错，拿它继续找文件，找不到就是正常 404。**宁可 404，不能崩。**
2. 整个 `createServer` 回调里 `new URL` 包 try/catch，畸形 Host 回 400。

注意 `decodeURIComponent` 在 `server.ts` 里有**三个**独立调用点
（静态路径 / 插件 UI / 模块 UI），只改一处是典型的「改了一处以为改完了」。
测试专门按三个调用点分别断言。

**十四、`sync-modules` 写错一次就是 26 个模块一起出问题。**

这个脚本每次 `npm run build` 都会跑，并且会**重写** `kugua.config.json` 的
`modules[]` 和根 `package.json` 的 `start` 脚本。它踩过两个坑，症状都很隐蔽：

| 坑 | 表现 | 为什么难发现 |
|---|---|---|
| 整体替换 `modules[]` | 运行时字段 `version` / `capabilityHash` 被抹掉 | 身份门禁**静默失效**：不报错，只是再也不拦任何东西 |
| 写回统一用 `
` | 内容相同但字节不同 | `--check` 永远报不一致，跑一次同步又没实质变更，最后这条门禁被当成噪声没人看 |

第一条尤其危险：它不产生任何错误输出，只是把「版本回退拦截」和「能力指纹
变化拦截」悄悄关掉了。要等到真的接入了有问题的外部模块才发现没拦住。

第二条属于「门禁失灵」的经典形态——**一个永远报警的门禁等于没有门禁**。
仓库在 Windows 下检出为 CRLF，而 `JSON.stringify` 只产 LF，所以必须
按原文件的行尾风格输出，而不是图省事写死 `
`。

顺带一个容易忽略的：模块列表**必须稳定排序**（process 优先、名字排序）。
扫描顺序由 `readdirSync` 决定，不排序的话同一份仓库两次运行可能得到不同
顺序，`--check` 会随机假报不一致。

测试做法：把纯函数拆到 `scripts/sync-modules-core.mjs`，它**不碰文件系统**
（给什么文本返回什么文本），读取目录和写盘留在 `scripts/sync-modules.mjs`。
原来的脚本是一整坨顶层过程代码，最后一行直接 `主()`，一 import 就会去改真实
配置文件——所以之前根本没法测。

### 六·七·九、`/api/file` 不能接受任意路径

编辑页要显示结果图，走的是 `GET /api/file?path=<路径>`。这个端点在
做图片编辑页之前是这么写的：

```ts
const 文件 = url.searchParams.get("path");
if (!文件 || !existsSync(文件)) { res.writeHead(404).end("Not Found"); return; }
发送文件(req, res, 文件);
```

**没有路径校验。** 实测：

```
GET /api/file?path=D:/Projects/KuguaStudio/package.json   → 200 + 文件内容
```

本机任何进程、以及**任何能向 127.0.0.1 发请求的网页**（CSRF）都能读整个磁盘。
这不是"潜在风险"，是当时就能复现的洞。

#### 白名单不能只做 `startsWith(tmpdir())`

那样仍然能读 `%TEMP%` 下任意程序的临时文件——别的软件的私有数据、
凭据、聊天记录缓存。放行范围应该是「**平台自己写的、且本来就要展示给前端的**」：

| 目录 | 谁写的 |
| --- | --- |
| `kugua-drop/` | `/api/writeTempFile`（拖拽上传落地） |
| `kugua-clip/` | 剪贴板图片 |
| `kugua-image-<id>/` | 图片模块的会话目录（编辑页） |

三个要点：

1. **`realpathSync` 之后再比**。不解析就比，`kugua-drop/../../secret`
   和指向仓库外的符号链接都能绕过。
2. **`startsWith(根 + sep)` 而不是 `startsWith(根)`**。后者会让
   `D:\_TempXXX\...` 通过 `D:\_Temp` 的检查。
3. **id 段按规则校验**（`[A-Za-z0-9_-]{1,64}`）。只认前缀不认 id 的话，
   前缀判断会把 `kugua-image-` 这种空 id 也放进来。

#### 拒绝用 403 不用 404

路径存在但不在白名单里，回 403。回 404 的话用户会以为"我路径写错了"，
去检查拼写——方向完全错了。

#### 函数测对了不等于端点接上了

写了 `允许读取的路径()` 并且给函数测了 15 条，全部通过。
然后故意把端点里的 `!允许读取的路径(文件)` 判断删掉——**15 条测试依然全绿**。

因为那些测试调的是函数本身，从来没有验证过端点有没有调用它。
所以补了两条读源码的接线测试：

```ts
const 源 = readFileSync(new URL("../src/server.ts", import.meta.url), "utf8");
const 端点 = 源.slice(源.indexOf('url.pathname === "/api/file"'));
expect(端点.slice(0, 400)).toContain("允许读取的路径(文件)");
```

这类「纯函数 + 接线」的组合，**两边都得测**。只测纯函数是最容易漏的一种。

### 六·七·十、长生命周期的临时目录必须有三层清理

`magick.ts` 里的 `用临时目录()` 是"进去 → 干活 → 立刻删"，生命周期一次调用。
图片编辑页需要的是相反的东西：用户拖滑块、翻帧列表期间，文件得一直躺在盘上。

于是有了会话目录 `<tmp>/kugua-image-<会话id>/`。清理必须有三层，缺一层就会
在 `%TEMP%` 里攒垃圾：

| 层 | 触发 | 覆盖的情况 |
| --- | --- | --- |
| 1 | 前端调 `image.session.release` | 关页面、换图 |
| 2 | 模块退出钩子（`注册` 返回的函数） | 正常退出、重启 |
| 3 | `清掉过旧会话()` 每次新建会话时扫一遍 | **强杀、断电、浏览器崩溃** |

第 3 层不能省。前两层都是"礼貌退出"路径，`taskkill` 一个都不走。
没有兜底的话用户 `%TEMP%` 会一直长胖，而且没人会想到是图片模块干的。

判定用目录的 **mtime** 而不是创建时间：长时间编辑的页面会不断写新结果图，
mtime 一直在更新，不会被误删。

#### `rmSync({force: true})` 不能用来判断"删没删"

```ts
let 删了 = false;
try { rmSync(目录, { recursive: true, force: true }); 删了 = true; } catch {}
```

目录不存在时 `force: true` **不报错**，所以这段代码永远返回 `true`。
幂等的 `release` 调用会一直声称"已删除"。

正确写法是先看存不存在，删完再看一遍：

```ts
if (existsSync(目录)) {
  rmSync(目录, { recursive: true, force: true });
  删了 = !existsSync(目录);
}
```


### 六·七·十一、模块 `界面` 页：`ui.entry` 不是 `entry`

模块可以在 `启动模块()` 里声明一个 `界面` 页，WebUI 会把它作为一个标签页
用 iframe 打开。定位页面用的字段是 `ui.entry`，它**相对模块进程入口所在目录**。

原来 WebUI 错用了 `entry`——那是**进程入口**（`dist/index.js`）。于是：

| 请求 | 拼出来的路径 | 结果 |
| --- | --- | --- |
| `/module-ui/image/` | `dist/ui/index.html` | **200**，页面正常显示 |
| `/module-ui/image/editor.css` | `dist/editor.css` | 404 |
| `/module-ui/image/editor.js` | `dist/editor.js` | 404 |

注意第一行：页面能打开。因为回落 `index.html` 时用的相对路径恰好带了 `ui/`
这层，和错算的根凑成了正确路径。**首页能开、样式脚本全丢**，第一反应是
「构建时没拷静态资源」，去查 `copy-ui.mjs`——查半天也查不出来，因为它是对的。

正确算法：

```ts
const 入口目录 = dirname(resolve(仓库根, 项.entry ?? ""));
const 根 = dirname(resolve(入口目录, 声明));   // 声明 = 项.ui?.entry
```

还有一处配套：根已经算到 `ui/` 目录了，所以回落页面时只能用 `ui/index.html`
的**文件名部分**，用完整路径会拼成 `dist/ui/ui/index.html`。

### 静态资源要自己拷

`tsc` 只看 `.ts`。`src/ui/*.html|css|js` 不拷的话 `dist/ui/` 是空的，
上面那个 404 会以更彻底的形式重现。所以 `build` 脚本是：

```json
"build": "tsc -p tsconfig.json && node scripts/copy-ui.mjs"
```

拷贝脚本**先删再拷**，不是覆盖。只覆盖的话，源码里删掉的旧文件会永远留在
`dist/`，而前端可能还在引用它。

### 六·七·十二、编辑页的控件必须由声明生成

编辑页里没有 `rotate`、`resize` 这些字符串（除了「应用」时拼动作名）。
所有控件是照着 `image.actions.declare` 返回的那张表渲染的：
`number` 出滑块、`number` + `档位` 出下拉、`string` + `选择` 出下拉、
`boolean` 出勾选。

这样加一个动作不需要改前端一行，也就不会出现「模块加了参数、前端没跟上」
这种只在用户点下去时才暴露的问题。

但「由声明生成」只在**声明的形状被正确理解**时才成立。真机验证抓到两个：

#### 档位是对象数组，不是标量

```ts
档位?: { 值: number; 标签: string }[];
```

前端第一版写的是 `o.value = String(档)`。症状：下拉框能出来，但每个
`option` 的 `value` 都是 `"[object Object]"`，`默认值` 对不上任何一项，
于是**选不中、框是空的**。看起来像「这个动作没有可选值」。

#### 没有默认值的数字参数不能用滑块

`resize` 的 `width` / `height` 语义是「留空就按比例算」。滑块天生无法
表达「空」——它总有值。用户只是想看看别的参数，手指扫过滑块就把 `width`
写成了范围中点 **10001**，意图和他的本意完全相反。

现在规则是：**有 `默认` 才用滑块，没有就用输入框**（带 `placeholder` 提示可以留空）。

### 六·七·十三、实时预览在前端做，松手才真调后端

拖滑块时发请求是不行的：一次 ImageMagick 约 65ms 启动 + 处理时间，拖动
过程中每帧都发，队列会堵死，用户看到的是几秒前的画面，还以为卡住了。

分工按动作的几何/颜色性质来：

| 动作 | 前端怎么预览 |
| --- | --- |
| 旋转 / 缩放 / 翻转 | CSS `transform`，0ms |
| 反色 / 灰度 / 做旧 | CSS `filter`，近似 |
| 切边 | Canvas 叠一层线框 + 压暗蒙版 |
| 拆帧 / 合成 / 超分 | 不做，直接按钮触发 |

**没有声明预览方式的动作什么都不做。** 假装能预览比不能预览更糟——
用户拖了没反应，会以为参数不生效。

前端预览只是「大概」：CSS 灰度的系数和 ImageMagick `-colorspace Gray` 不同，
旋转插值算法也不同。所以松手后立刻用真结果替换，界面上也不做
「预览即最终结果」的暗示。

### 六·七·十四、34 个动作要一次改完，不能逐个加

编辑页要的是**路径**，聊天框要的是 **base64**。逐个动作加 `path` 意味着
改 34 处，而漏改的表现是「前端显示不了图」而不是报错。

所以注册处包了一层：

```ts
const 图片动作 = (名, 干活) => {
  客户端.onRequest(名, async (params) => {
    const 结 = await 干活(params);
    if (!结?.base64) return 结;
    return 落会话(结, params?.session, 名.replace(/^image\./, ""));
  });
};
```

- 传了 `session` → 额外写文件、多一个 `path` 字段，**base64 照旧返回**
- 没传 `session` → 行为与改造前一模一样

`归一参数()` 里也要把 `session` 加进透传白名单：它不属于任何动作的业务
参数，但每个编辑页请求都会带。不透传的话处理完就丢了会话号，
结果写不回会话目录，前端拿到一个没路径没 base64 的空对象。

（**不**把 `session` 写进 34 个动作的参数声明：那样能力清单里每个动作都会
多一个「会话号」，聊天框和外接方看到会很困惑。）


### 六·七·十五、路径契约漏了多图参数

第 3 步给单图建了路径契约：`取图Buffer()` 同时认 `base64` 和 `path`。
**多图参数 `images` 没跟着改**——它一直只认 base64 数组。

编辑页手里的图是路径（不然 30 帧 GIF 要传 3.7MB），于是拼接动作收到的
是一串 `D:\...\a.png`。而这些字符串被当 base64 解码：

```js
Buffer.from("D:\x\a.png", "base64")   // 不抛异常，返回一堆垃圾字节
```

ImageMagick 欣然把垃圾当图处理完。**不报错，不警告，给出结果**:

| 操作 | 期望 | 实际 |
| --- | --- | --- |
| 两张 200x150 纵向拼接 | 200x300 | **600x400** |

这种错比崩溃难查得多——界面上有一张图，状态栏有尺寸，只是数字不对。
用户未必看得出，看不出就一直错下去。

修法是在注册层统一转换，一处覆盖全部多图动作：

```ts
const 图片动作 = (名, 干活) => {
  客户端.onRequest(名, async (params) => {
    const 结 = await 干活(补多图(查声明(...), params));
    ...
```

`补多图()` 按声明表找出所有 `类型: "images"` 的参数，把其中**看着像本地路径
且文件真实存在**的项读成 base64。判断不靠「长度是不是 4 的倍数」这类猜测：
base64 里不会出现盘符冒号或路径分隔符。

### 关键：转换必须返回新对象

```ts
出 ??= { ...入 };   // 对
出 ??= 入;          // 错
```

原地改让调用方拿到被换过的参数。如果将来加重试，第二次拿到的就是
「已经是 base64 的 images」，而 `补多图` 会把它当路径去 `existsSync`——
`"iVBORw0KG..."` 这种串在某些系统上真的会被当成相对路径，
`existsSync` 返回 false 后原样保留，恰好又能工作，于是 bug 藏到
某天某个文件恰好同名才发作。**纯函数不原地改入参**，这条没有例外。

### 六·七·十六、多帧结果的帧列表也走路径

`images` 里装的是 base64，30 帧 3.7MB。编辑页要显示帧缩略图时，
把这些全传给前端等于把第 3 步省下的开销又花回去。

所以 `落会话()` 额外做一件事：把 `images` 逐个写进会话目录，返回一个
`frames` 路径数组。

- `images` **原样保留**——聊天框和外接方都在用，删了就是破契约
- `frames` 是新增字段，旧调用方不认也不受影响
- 帧统一存 **PNG**，不存 JPEG：GIF 帧可能带透明通道，存 JPEG 会丢

前端拿到 `frames` 后交给 `<img src="/api/file?path=...">`，浏览器自己
流式加载、吃 HTTP 缓存，横向滚动时没滚到的帧根本不会请求。

### 六·七·十七、`?? []` 之后 push 是无效的

```js
const 列 = 状态.多图[键] ?? [];
列.push(路径);        // 白 push
```

数组是这次调用新建的，push 完没挂回 `状态.多图`。下一次渲染又取到一个
新的空数组。症状是**点「加入当前图」毫无反应，也不报错**。

正确写法只有一种：

```js
const 列 = (状态.多图[键] ??= []);
```

这类 bug 的特征很统一：**读的时候给了默认值，写的时候忘了挂回去**。
凡看到 `x[k] ?? []` 后面跟 `.push()` / `.splice()`，就该警觉。


### 六·七·十八、同步纯函数与声明表：只能生成，不能 await

聊天框的指令路由器是个**同步纯函数**：

```ts
if (/^旋转/.test(文本)) return 需图("image.rotate", { degrees: 90 }, "图片旋转");
```

它拿到一句话就得立刻给出「目标模块 + 动作 + 参数」，没有 await 的余地——
拿声明表要么请求模块（异步，还得处理模块没启动），要么在启动时预载
（渲染层启动顺序里塞一个网络请求，失败就没法路由）。

所以默认值只能写字面量。于是有了**两份描述**：声明表说 `rotate.degrees`
默认 0、界面默认 90，路由器说「请输入 90」。

现在两份值恰好一致。但**没有任何机制保证以后一致**——改了声明表忘了
改路由器，症状是「编辑页里默认 90、聊天框里默认 0」，不报错、不崩、
只在对比时才发现。

### 办法：生成，然后测

`scripts/gen-image-defaults.mjs` 从 `dist/actions.js` 抽出默认值，
产出一份纯数据 `packages/webui/src/renderer/image-defaults.ts`。
路由器引用它，不再写字面量。

单一来源仍然是 `actions.ts`。生成物只是它的一个子集被**编译**成
同步可用的常量——和 `sync-modules.mjs` 一样的思路。

挂在根 `build` 的最前面：

```json
"build": "node scripts/sync-modules.mjs
       && npm run build -w @kugua/module-image
       && node scripts/gen-image-defaults.mjs
       && npm run build --workspaces --if-present"
```

顺序有讲究：**先生成模块产物，再抽默认值，最后编译 webui**。
反过来生成脚本读到的是上一次的 dist。

### 生成的隐患：忘了重新生成

最大的风险是「改了声明表、跑测试、全绿」——因为测试读的就是那份旧常量。

所以 `image-defaults.test.ts` 直接比对两边：

```
→ grid.scale 与声明表不一致——请跑 npm run gen:image-defaults
```

这条断言是整套机制的**唯一守门人**。没有它，生成物就只是另一份
「看起来同步、实际随便飘」的复制品。

### 抽纯函数，否则测试根本跑不起来

想在测试里真跑一次路由器，碰到 `document is not defined`——
它顶层 import 了 `02-chat-core`、`03-preview`、`10-chat-page`，
这些模块在 import 时就摸 DOM。

这是小组件那边踩过的同一个坑（`19-widgets.ts` 依赖 DOM 不可测，
决策逻辑抽 `widget-layout.ts`）。同样的处理：把「某动作某参数默认值是
多少」抽成 `image-command-defaults.ts`，只依赖纯数据，Node 里随便 import。

### `?? ` 与 `||` 在这里不是风格问题

```ts
const 值 = 表[动作]?.[键];
if (值 === undefined) return 兜底;   // 对
if (!值) return 兜底;                // 错
```

`cut.percent` 的默认值是 `false`。用 `||` 判断会把 `false` 当成「没取到」，
换成兜底值——而兜底值如果是 `true`，语义就整个反了（从「按像素切」
变成「按比例切」）。有专门一条测试盯着这个。


### 六·七·三、主动退出通知（`platform_exit`）

上面的断线处理针对的是**意外**断开。但还有一类是**用户自己要的退出**——
在设置页点「退出平台」或托盘点「退出」。这类不该套用"可能出问题了、
正在重连"的措辞，更不该让用户干等。

桌面端尤其明显：壳判断后端死活靠端口探测，而那个探测为了容忍「重启」
（先杀旧进程再起新进程的几秒空窗）设了连续 10 次失败才判定退出。
手动退出时根本没有这个需求，却会继承同样的十来秒延迟——表现就是
「点了退出，然后卡住失联」。

所以后端在退出前**主动推一条 WebSocket 消息**：

```json
{ "type": "platform_exit", "reason": "shutdown" }
```

| reason | 含义 | 前端行为 |
|---|---|---|
| `shutdown` | 真的退出 | 显示「平台已退出」→ 1.2 秒后自行关窗 |
| `restart` | 只是重启 | 显示「正在重启，请稍候」→ **不关窗**，等重连 |

区分这两者是必须的：重启后平台会回来，这时把窗口关掉反而是错的。

几个实现要点：

- **先广播再收东西**：此刻连接都还活着，消息能立刻发出。整段包在 try 里，
  单条发送失败不能阻塞退出流程。
- **收到后停掉重连定时器**（`平台已退出` 标志）：否则进程都没了还在每 1.5 秒重试。
- **关窗走 `quit_app`**，不用 `window.close()`：WebView2 里后者只对脚本自己
  打开的窗口有效，普通窗口调用会被静默忽略（表现为"点了没反应"）。
- **延迟 1.2 秒再关**：让提示先渲染出来，否则窗口直接消失，用户会以为
  "点了退出之后程序崩溃了"，而不是"它按我说的退出了"。
- **浏览器环境跳过关窗**（标签页不允许自我关闭），只留提示。

端口探测保留，降级为**兜底**——后端崩溃/被强杀时没人能发消息，只能靠它。

### 六·七·四、消除启动白窗

窗口创建时若直接 `.visible(true)`，用户会先看到一片白：WebView2 **从建好
窗口到真正渲染出页面之间有几百毫秒空档**，那段时间窗口里是空的。

所以壳里的窗口是**隐藏创建**的，由页面在画完首帧后调 `show_window` 显示。
难点在"什么时候算画好了"：

| 时机 | 是否够 | 原因 |
|---|---|---|
| `DOMContentLoaded` | ✗ | 只保证 DOM 解析完，**此时还没绘制** |
| 固定延迟 N 毫秒 | ✗ | 定短了慢机器照样白，定长了快机器白等 |
| **双层 `requestAnimationFrame`** | ✓ | 表示浏览器至少已完整画过一帧 |

兜底是必须的：页面若加载失败就没人来报告，窗口永远不出现——那比白屏更糟。
壳里挂了 8 秒超时强制显示（`兜底显示`），宁可白屏也不能变成
"程序启动了但没窗口"。

> **注意**：自定义命令要在**两处**登记才生效——`capabilities/default.json`
> 的 `permissions` 列表，以及 `permissions/<命令名>.toml`（定义 `identifier`
> 与 `commands.allow`）。只加前者会报 `Permission xxx not found`。
> 漏了这一步的表现是「命令调不到、退回 8 秒兜底」，很容易误判成前端问题。

### 六·七·五、启动闪屏

启动时先出一个独立的透明小窗（发光圆球 + 进度条），主界面备好后渐变切换。

原来启动流程是**同步阻塞**在 `main()` 里的：

```
单例检查 → 启动侧车 → 等端口（最长 60 秒） → 才创建窗口
```

后端启动期间一个窗口都没有，用户双击后看到的是「什么也没发生」。
所以「启动侧车 + 等端口」挪进了 `setup` 的后台线程，闪屏在它之前创建。

**进度不做假动画**。四个阶段对应真实事件：

| 阶段 | 进度 | 触发者 |
|---|---|---|
| 连接中 | 18% | 闪屏自启 |
| 主控就绪 | 62% | 后台线程等到端口 |
| 界面就绪 | 92% | 页面报告首帧 |
| 完成 | 100% | `show_window` 前一刻 |

匀速条和后端真实进度脱节，用户会看到「条满了但界面还没出来」，
比没有进度条更让人焦虑。最后 8% 留给真正的主界面。


### 六·七·六、小组件布局：三处「看起来对、其实没生效」

小组件的第二三步（响应式降级、拖拽、仪表盘设置）写完后单测全绿，
真跑起来三个问题一起冒出来，而且**一个都没报错**。记在这里是因为
它们都属于「沉默失败」，靠读代码很难发现。

**一、参数名对不上，设置页改什么都存不住。**

渲染层发 `{ config: 节 }`，主控读 `{ 配置: 节 }`。`config.set` 拿到
`undefined` → `归一配置节(undefined)` 给出一套默认方案 → 照常写盘、
照常返回 200。界面刷新后设置没了，日志里一片安静。

守门的是 `packages/main/test/widgets-contract.test.ts`：不做集成测试
（起进程慢且偶发），而是**读两边源码把键名抠出来断言相等**。这类错误
单看任何一边都发现不了，必须把两边的字面量摆在一起。

**二、flex 默认 `stretch`，小组件被拉成 847px 高的竖条。**

`.wg-slot-top` 没写 `align-items`，子项被拉满槽位高度。
它还**连累了拖拽**：`dragover` 按「指针在目标上半还是下半」决定插前插后，
高度 847 时下半区间够不着，怎么拖都插在前头，看起来像拖拽坏了。

教训是「一个样式 bug 可能伪装成另一个功能 bug」。所以定位拖拽问题时先量了
`getBoundingClientRect()`，看到 `height: 847` 才找到真凶。

**三、拖拽监听器可能永远绑不上。**

`绑定拖拽()` 用全局布尔挡重复绑定。但首次调用在 `初始化小组件()` 顶层，
那时 `#workspace` 还没挂进 DOM，`确保槽位()` 直接返回、循环拿不到任何容器——
**布尔却已经置 true**。之后槽位建好了也永远不会再绑。

改成 `WeakSet<HTMLElement>` 按容器记录。凡是「只做一次」的逻辑，用「已经做成了」
而不是「已经试过了」作判据。

**顺带定下的两条设计取舍**：

- **拖拽不跨槽位**。拖到别的区域看着自由，但会让用户把自动布局当成手工排版，
  换个窗口宽度就全乱。要在区域之间移动，设置页里选「区域」更明确。
- **宽度只作上限，不往上抬**。`显著度` 表达「这个指标重要」，不是「它该占多宽」；
  1366 宽 + 侧栏展开时，三个 primary 大卡会把顶部条挤成两行。
  用户显式指定外形时无条件尊重——那是他说了算，不是自动推算。

**主窗口等后端就绪后才建**。提前建的话它加载的是还没起来的地址，
得到「连接被拒绝」错误页且不会自己恢复；补救靠重载，而重载时机又和
页面自身生命周期打架（`eval` 可能落在导航中被丢弃）。

**交接顺序**：先 `show()` 主窗口（此刻闪屏还置顶在上面），再让闪屏淡出。
反过来的话中间会闪一下桌面。

两个必须注意的窗口生命周期问题：

1. **闪屏关闭不能触发整个壳退出**。`CloseRequested` 一律 `exit(0)` 的话，
   闪屏交接完一 `close()`，刚显示出来的主界面会跟着没掉，壳在 4 秒后
   无声退出（且无任何日志）。→ 用 `窗口.label() != "main"` 判断。
2. **窗口计数短暂归零不能触发 `ExitRequested`**。闪屏关闭那一瞬主窗口
   还没完全就位。→ 只要主窗口还在就 `api.prevent_exit()`。

闪屏 HTML 用 `include_str!` 编进二进制、走 data URI 加载，不依赖外部文件。
**必须是 base64 形式**（`data:text/html;charset=utf-8;base64,...`）：
直接拼 HTML 原文时，换行符会让 URL 在第一行断掉、`+` 会被解码成空格，
结果是窗口「可见」但页面空白——透明窗口配空内容，看上去就是闪屏没出现。
这需要 `Cargo.toml` 开启 `webview-data-url` feature（默认不支持）。

### 为什么选 Tauri 而不是 Electron

关键约束是**不被用户浏览器的崩溃牵连**。PWA 看似是选项，但它**不包含任何渲染引擎**——
Chrome 装 PWA、Edge 装 PWA，用的仍是各自的浏览器内核，浏览器出问题照样一起完蛋。

Tauri 用的是 Windows 10/11 自带的 **WebView2**，与用户的 Chrome 是完全独立的进程树与安装。
相比之下 Electron 要自带 ~150MB Chromium，而本项目不需要那份额外体积。

### 壳只做三件事

`packages/desktop/src-tauri/src/main.rs` 刻意保持极薄，**不含任何业务代码**：

1. 拉起 WebUI 侧车（`node packages/webui/dist/server.js --no-open`）
2. 等端口就绪，把主窗口指向 `http://127.0.0.1:<port>`
3. 关窗时收走侧车，不留孤儿 node

业务逻辑全在 Node 侧，所以 Chrome 版与 Tauri 版不会分叉。

### 前后端契约：`window.kugua` 不变

`kugua-shim.ts` 仍注入同一套 `window.kugua`，只在**窗口控制**上分支：

```
const 是桌面壳 = typeof window.__TAURI__ !== "undefined";
window.kugua.window = 是桌面壳 ? 桌面窗口控制() : 浏览器窗口控制();
```

浏览器端：窗口按钮自动隐藏，窗口方法为空实现。
桌面端：转发到壳命令，按钮可见。

### 两个踩过的坑（改代码前务必看）

**坑一：窗口控制不能用 Tauri 内置的 `window.*` API。**

capability 的 `remote.urls` 对 `http://127.0.0.1:<port>` 这类远程页面经常匹配不上，
表现为「调了 `close()` 但窗口毫无反应、也不报错」。
解法是改用**本应用自定义命令**（`quit_app` / `minimize_window` / `toggle_maximize` / `is_maximized`），
并在 `src-tauri/permissions/` 里为每个命令写权限文件。

**坑二：侧车进程必须有三层保障。**

| 层 | 作用 |
|---|---|
| `CloseRequested` 钩子 | 正常关窗时同步 `taskkill /T` 收掉侧车进程树 |
| `RunEvent::Exit` | 进程退出时兜底再收一次 |
| **Windows Job Object** | 进程无论怎么死（崩溃/被任务管理器杀），系统连带收掉子进程 |

Job Object 是最后一道防线：没有它，壳被强杀会留下跑着的 node。

另：`CloseRequested` 里清理时**不要**调 `app_handle().exit()`——它要在关闭流程中重入事件循环，
实测会把进程卡成「WebView 已退、窗口句柄仍在」的僵尸。同步收完侧车后直接 `process::exit(0)`。

### 构建

```bash
npm run build                                # 先构建 WebUI
node packages/desktop/scripts/build.mjs      # 出 exe
debug 版：加 --debug
```

不依赖 `cargo tauri` CLI 也能出可执行文件（`tauri-build` 在编译期生成 context）；
只有「打 NSIS 安装包」才需要 `cargo install tauri-cli`。

## 六·七附、可装卸性验证：五层测试怎么钉住「模块能拆」

> 这一节回答一个问题：**我们凭什么说架构是解耦的？**
> 凭 26 个模块都能单独装、单独卸、装来装去不互相影响——而且有测试守着。

### 为什么要专门做这件事

早期所有模块是一起开发、一起调试的。这种背景下「解耦」很容易变成一句口号：
代码里确实没有互相 `import`，但**运行时**的耦合往往藏在别处——

- 前端硬编码了一批指令到模块的映射（`04-router.ts` 里 28 处）
- 某个模块启动失败会不会拖垮别人
- 模块卸掉后，它的界面页有没有从列表里消失
- 插件（同进程）之间的隔离比模块（独立进程）脆弱得多

这些都不是读代码能确认的，只能**真的装卸一遍**。

### 五层，从最便宜到最贵

| 层 | 文件 | 测什么 | 为什么放这一层 |
|---|---|---|---|
| 一 | `isolation-static.test.ts` | 模块间零 `import`、不 import main/webui、`package.json` 依赖面干净 | 纯静态，毫秒级，能天天跑 |
| 二 | `isolation-runtime.test.ts` | 零模块启动、逐项累加、卸中间模块、坏模块不拖累好模块 | 真起进程，但要跑几十秒 |
| 三 | `isolation-plugins.test.ts` | 插件装卸、删目录自动卸载、装 A 卸 A 装 B、坏插件留下 error 记录 | 插件同进程，隔离更脆弱 |
| 四 | `isolation-ui.test.ts` | 模块 `界面` 页随模块来去、零模块时 WebUI 照常、页面文件缺失 404 | 跨进程，最容易破 |
| 五 | `isolation-commands.test.ts` | 聊天框指令打到不存在的模块时，错误要**点名模块** | 硬编码路由的兜底 |

共用 `isolation-sandbox.ts`：只起主控、隔离 `KUGUA_GLOBAL_LOCK` / `KUGUA_DATA_DIR` / 临时配置，
碰不到用户正在跑的实例。

### 三个「测试自己骗自己」的坑

这一轮真正花时间的地方不是写断言，而是**发现断言根本没在测产品**。
三次反向验证都「没红」，查下去问题都在测试侧：

#### 一、沙盒包装吃掉了错误原文

`沙盒.请求()` 会把错误包成 `` `${目标}.${动作} 失败：${原错}` ``，方便定位是哪条挂的。
于是「错误信息里要含模块名」这句断言**永远成立**——因为包装里就有目标名。

修法：加 `裸请求()`，不包装，专门给「验底层行为」用。

#### 二、正则太宽松

`toMatch(/food|不存在|未找到|未知/i)` 里，`` `目标模块不存在` `` 含「不存在」，照样匹配。
断言看着很严，实际测不出「有没有点名模块」。

修法：改成 `toContain("food")`。守门人只守一件事。

#### 三、`node -e` 的字符串替换静默失效

反向验证靠「临时撤掉修复，测试必须红」。这一轮有 **四次** 撤掉后测试仍然绿，
排查后发现是替换串没匹配上——`s.replace(...)` 找不到就原样返回，**不报错**。

这是最阴的一类：你以为验过了，其实什么都没改。

修法（写进习惯）：

```js
const 前 = s;
s = s.replace(旧, 新);
if (s === 前) { console.log("未命中"); process.exit(1); }
```

以及改完 **先 grep dist 确认改动进了产物** 再跑测试。

### 真抓到的一个 bug

第三层「坏插件留下 error 记录」这条把问题逼出来了。

`加载全部()`（启动路径）在 catch 里写 `插件表.set({状态:"error", 错误})`，
但 `加载()` 自己**不记**。于是**运行期动态投放**一个坏插件时（写错语法、
`import` 不到包、不是 `BasePlugin` 子类），只打一行日志，插件表里什么都没有：

- `plugins.list` 查不到
- 界面上完全看不见
- 用户看见目录里有东西、界面里没有，也不知道去哪看日志

静默消失比报错难查得多。修法是把 `加载()` 拆成 `加载()` + `加载内部()`，
`加载()` 统一在 catch 里记表再抛——两条路径就一致了。

反向验证：把 catch 里的记表去掉，测试精确红在
`` `坏插件没有留下 error 记录` ``。

### 一个认知纠正：「主界面本身是插件化的」

这个说法容易误解。实际结构是：

- **主界面 = `webui` 包**，它**不可拆卸**。拆了就没有任何 UI 了。
- **模块贡献的是页面**，通过 `界面: { title, entry }` 声明，挂在框架里。

所以「无主界面模块」准确说是「**没有任何模块贡献页面**」——此时框架照常可用
（聊天框、配置页、日志页都在），只是「模块页」那一栏是空的。
`isolation-ui.test.ts` 把这条边界钉死了：零模块时 `/api/status` 必须 200、首页必须能开。

如果哪天有人把聊天框也做成模块，那才会出现「无主界面模块 → 整个界面空白」。
当前不是这样。

### 插件契约的门槛（写测试时踩的）

手写测试插件连错三次，每次都表现成「插件没被扫描到」，实际原因各不相同：

1. **必须是 ESM**（`import`/`export default`），写成 `module.exports` 会被判
   「默认导出不是 BasePlugin 子类」
2. **目录要在仓库内**：临时目录里的插件 `import` 不到 `@kugua/plugin-sdk`
   （Node 从文件所在目录往上找 `node_modules`，临时目录上面没有）
3. **`定义插件` 的第二个参数是英文键且 `version`/`description`/`author` 必填**，
   缺一个就是 `Cannot read properties of undefined (reading 'trim')`

这三种失败都只写 `状态:"error"` + 一行日志，不主动看错误字段的话，
表现得就像「插件没被扫描到」。这本身说明**插件契约的报错可以更好一些**——
但那是另一个里程碑的事，先记在这里。

### 六·七附·补、模块单测的三类价值

给还没测试的模块补单测时，真正有用的不是「覆盖了多少行」，
而是**能抓出哪三类问题**。这一轮（translate / qrcode / avatar）各自代表一类：

#### 一、静默失败的链路

`translate` 是 `抓网页 → 正则抠译文 → 解码实体`，三个环节全都是静默失败：
拿不到 200 就 `return ""`、正则找不到容器就 `null`、最后回退成原文。
上游一改版，用户看到的是「译文和原文一模一样」而不是报错。

对这种链路，测试要验的是**每一段的接缝**，而不是「端到端能出结果」：

- `解析译文` 找不到容器时返回 `null` 而不是 `""`——两者必须能区分
  （`null` = 上游改版了；`""` = 容器在但内容空）
- 解析那一步**不解实体**，原样把 `&amp;` 交给下一段。合在一起就测不出哪段坏了

写测试时还抓出两条「我以为的行为与实现不符」：

1. `&amp;lt;` 我以为只解一层得 `&lt;`，实际是 `<`——因为**链式 replace 相互影响**
   （`&amp;` → `&` 之后，`&lt;` 那条 replace 紧接着又命中）。
   浏览器是一次扫描、不连锁，所以这里与浏览器行为**不同**。已钉住并写清原因。
2. `div[^"]*?"result-container"` 这个正则**不允许属性值里带引号**，
   所以 `<div id="x" class="result-container">` 抠不到。
   Google 实际页面里 `result-container` 是第一个属性，所以能用——但这是硬限制。

#### 二、错了也「看起来正常」的默认值

`qrcode` 生成二维码，参数错了图照样能扫，肉眼绝对发现不了。
最典型的一条：

```ts
const 边距 = p.边距 || 4;        // 错：用户要 0（贴边）会被换成 4
const 边距 = typeof p.边距 === "number" ? p.边距 : 4;  // 对
```

这类问题只有**比对返回值**能发现，所以测试要断言具体数值而不是「有值」。
同一类还有：`尺寸` 只认正数（0/负数/NaN/字符串全退回 300）、
纠错级别非法值退回 `M` **不抛错**（写错一个字母时给图比给报错有用）。

#### 三、手写字节解析

`avatar` 的 `图片尺寸` 读 PNG/GIF/JPEG 文件头。写错一个偏移量的表现是
**返回 `{0,0}`**——不抛错、不崩，只是功能悄悄失效。

所以每种格式都验**宽高分别对不对**，而不是「能读出来」：

| 格式 | 陷阱 |
|---|---|
| PNG | 大端，宽在 16、高在 20 |
| GIF | **小端**，宽在 6、高在 8 |
| JPEG | 逐段扫 SOF；段内**高在前、宽在后**（与直觉相反）；`C4`/`C8`/`CC` 同段但不带尺寸要跳过 |

宽高故意取不同值（`1024×32` 与 `32×1024`），两个偏移写反了会立刻红。

#### 附带修了守门人自己的一个误报

`isolation-static.test.ts` 原来用 `目标.includes("modules/av/")` 判断跨模块引用。
`...\modules\avatar\src\parse.ts` 里包含 `modules\av`，于是
**avatar 引用自己目录里的文件被判成「引用了 av 模块」**——模块名有前缀关系就会踩。

改成按**路径段**比较（`resolve(模块根, 名) + sep` 作前缀）。
修完做了反向验证：往 avatar 里植入一行真的 `import "../../text/src/index.js"`，
测试照样红。**修误报不能把守门人改成瞎的**。

#### 附：两类「算错了不报错」的纯计算

补 monitor 与 mcp-client 时遇到的，正好代表两个常见类别，记下来：

##### 一、会直接显示给用户看的数值

monitor 算出来的数全都要上界面。算错了不抛错、不崩，**只显示一个错的数**：

| 情形 | 不兜底的后果 |
|---|---|
| 磁盘 `total` 为 0 | `used/total` 得 `NaN` → 界面显示「NaN%」 |
| `free > total`（虚拟机、配额目录） | `used` 变负数 → 显示「-50%」 |
| 监控间隔传 0 | `setInterval(0)` 退化成每帧一次 → **打满一个核** |

所以这几处测试的断言必须是**具体数值**而不是「有值」。
另外那条间隔还有一层：`采集快照` 内部 `采样CPU使用率` 本身要阻塞 300ms
做双采样，间隔太短会让任务排队堆积——**下限 2 秒不是随便定的**。

##### 二、拼进全局键的名字

mcp-client 的前缀会拼成能力名（`前缀.工具名`），而能力名是主控的**全局键**。
拼错了的表现最阴：**接入成功的日志照样打**，但真去调那个能力时路由打不到。
日志里完全看不出来，只有实测才发现。

这类「字符串被当键用」的函数，测试要钉的是**键的合法形状**：

```ts
expect(能力名(前缀, "t")).toMatch(/^[A-Za-z0-9_.-]+$/);
```

而不是只测一个具体值。因为非法字符换成了下划线之后，
错误的前缀仍然「看起来是个字符串」，只有正则能把形状钉住。

#### 附三：复刻算法的「不要顺手修」

`chatmode` / `divination` / `food` 这些模块的算法是从原项目逐行搬的。
搬的过程中一定会遇到看着不合理的地方：

```ts
result = result.slice(0, -1) + sgn2[NextInt(sgn2.length)];  // 先补再砍，为什么？
sentences[NextInt(0, sentences.length - 1)];                // 闭区间，容易越界
if (!result) result = " ";                                  // 空结果给个空格？
```

第一反应是「这里能简化」。但**复刻类代码的正确性标准是「与原版行为一致」，不是「看起来更合理」**。
一旦改了，用户会觉得「怎么跟以前不一样了」，而这种回归极难定位——
因为改的人通常觉得改的是「明显 bug」，不会去写测试。

处理原则：

1. **不修**看着怪但无害的写法，只在旁边加注释说明「原版行为，不要改」。
2. **必须修**的（比如 `cron` 的周日永不触发，那是真错），修完要在更新日志里写明
   「与原版不一致，原因是……」，让用户知道这是有意的偏离。
3. 每条「怪行为」都要有测试守着。测试注释里写明「原版行为，不要改」，
   后来的人看到红色才知道自己动了什么。

典型例子：`chatmode` 的 `西医句` 在语料为空时会拼出 `undefined`。
这不是好行为，测试里却专门断言 `toContain("undefined")`——
因为修它属于「顺手改行为」，应该单独决策，而不是被一次重构带走。

#### 附二：cron 的「静默不触发」

scheduler 的 cron 实现里抓到一个典型 bug，值得单独记：

```ts
// 错：把 0（周日）映射成 7 再查
const 周值 = d.getDay() === 0 ? 7 : d.getDay();
const dow = 表达式.周.取值.has(周值);
```

`0 0 * * 0` 的取值集合是 `{0}`，`has(7)` 永远 false。
于是**写 0 的周日任务永远不触发**——而 0 是最常见的周日写法。

为什么这个 bug 能活这么久：它**什么都不报**。`下次运行` 在 5 年内
找不到匹配就返回 `null`，任务静静躺在列表里从不执行。
用户没法验证——他不可能守着看一周。

修法是两个都查。这类「把语义相同的两个值只处理一个」的坑在
时间/编码/单位换算里反复出现，所以测试要写成**对照式**：

```ts
expect(fmt(下次运行(解析Cron("0 0 * * 0"), 从)))
  .toBe(fmt(下次运行(解析Cron("0 0 * * 7"), 从)));
```

**两种等价写法必须给出同一结果**——这比分别断言某个具体时间更抗变化，
也更容易看出「有一个不对」。

另外 cron 测试有一条硬规矩：**全部用固定时间戳，不碰 `Date.now()`**。
任何「从现在算下一次」的断言都会在跨天、跨月、跨年时随机失败，
而偶发失败是最贵的失败——见 §六·七附「偶发失败必须有确定性复现条件」。

## 六·八、语音合成（引擎无关抽象）

详见《[语音合成设计.md](./语音合成设计.md)》。

核心是**把引擎变成可插拔实现**，上层只认一套接口：

| 分层 | 定位 | 引擎 | 显存 |
|---|---|---|---|
| `fast` | 实时对话，占用少输出快 | VoxCPM1.5（0.6B） | ~6 GB |
| `quality` | 有声书批处理，拟真可调情绪 | IndexTTS-2.5（1.5B） | 8–12 GB |
| `fallback` | 显存被占满时兜底 | sherpa-onnx（纯 CPU）/ Windows SAPI | 0 |

调度：显式 `engine` 只试指定者（失败即报错）；未指定则 `defaultEngine` → 按分层依次尝试，
第一个成功即返回。未配置的 `fast`/`quality` 引擎跳过，未配置的 `fallback` 引擎仍参与
（意义就是「别的都不行时还能出声」）。

音色统一为 `{ id, refAudio, refText, refLang, gptWeights?, sovitsWeights?, speakerId? }`，
零样本（参考音频克隆）与微调（权重对）两类共用，由引擎各取所需。
情绪统一为 `{ text, refAudio, intensity, vector }`，映射到 IndexTTS 的五种情绪控制方式，
其余引擎忽略不支持的字段。

能力：`tts.speak` / `tts.status` / `tts.voices`。

## 七、总线（Nigane）

- 传输：WebSocket 文本帧，主控监听 `127.0.0.1:24601`（可配置）。
- 拓扑：星型，主控是唯一服务端；模块间不直连。
- 消息：`hello / hello_ack / request / response / event / error / ping / pong`。
- 约定命名空间：`模块.动作`；能力动作即 `模块.动作`；作业动作 `job.*`。
- 协议演进只增加可选字段，不改变既有字段语义。详见《开发细则.md》。

## 八、知识库与资源管理

概要（详见《知识库设计.md》）：

- 文件系统为真源；SQLite 存索引、标签、关系、保存视图、位置；
- 标签持久化在**侧车文件**（`.mkg.json`）中，可随文件迁移；
- 检索：`LIKE` 升级为 **FTS5 全文索引** + 标签查询 + 保存的智能视图；
- 统一节点模型：文件 / 目录 / 笔记 / 素材 / 文本段 / 看板卡片；
- 支持导入去重（sha256）、回收站删除、按扩展名配置打开方式。

## 九、常驻、调度与开机

- **常驻**：主控注册为 Windows 服务（WinSW/NSSM）或"登录时"任务；子进程由主控守护并按需重启。
- **调度**：内置 cron（5/6 段）；额外提供 `启动/登录` 触发器，桥接 Windows 任务计划程序（`schtasks`）可选。
- **开机任务**：本质是"位置=启动"的调度任务，随主控启动执行一次。
- **日志**：内存环形缓冲 + 限流落盘；空闲时不产生周期性磁盘写。
  分级约定（级别是给用户判断“要不要理”的，不是排版）：
  - `debug` — 诊断细节（连接地址、样本、能力清单）。**默认在系统日志页收起**。
  - `info` — 状态变了一件事（模块上线、配置被改、用户发起的实际操作）。
  - `warn` — **配置错了 / 能力降级 / 能跑但不对**。例：库文件不存在、未配 token。
  - `error` — 本次操作失败。

  **正文里不再重复写「警告：」「WARN」**——级别已经标在列上了。
  **模块输出靠级别前缀传级别**：Node 只有 stdout/stderr 两个频道，module-kit 在托管模式下
  给每行加 `\u0001kugua:<级别>\u0001` 前缀，主控按它还原——否则模块写的 `console.warn` 到了
  主控就变成 info，**报过错却看着一切正常**。

## 十、安全

- 模块与能力两级权限声明，最小授权；
- `exec` 能力默认不暴露；脚本任务限定工作目录与目标 allowlist；
- 所有能力调用与作业执行审计；
- 总线仅监听本机回环地址；令牌可选启用；
- MCP server 默认 stdio，不监听网络；如需 HTTP 需显式开启并绑定回环。

## 十一、非目标（明确不做）

- 不做云服务/多租户/账号体系；
- 不把 AI 作为必须依赖（无 AI 时全部功能仍可用）；
- 不深挖脆弱的第三方平台（Telegram / B 站直播 / 贴吧爬虫 / VTubeStudio 等），仅保留可选桥接位；
- 不做"什么都塞进数据库"——原始文件永远由文件系统持有。

## 十二、路线（详见《改造清单.md》）

1. **地基**：能力注册表 + 目录/协议规范 + 清理历史包袱；
2. **知识库**：MKG 数据模型升级（FTS5 / 侧车 / 保存视图 / 位置）；
3. **入口**：中文指令解析统一走注册表；GUI 命令面板接注册表；
4. **互操作**：MCP server（暴露平台）→ MCP client（接入外部项目）；
5. **长任务**：脚本/爬虫/安全测试的 Job 运行时 + 审计；
6. **常驻**：服务化 + 开机任务 + 调度桥接；
7. **功能重写**：按新约定逐个重写功能模块（图片/文本/历法/…），去掉历史实现。
