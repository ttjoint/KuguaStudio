# 功能复刻准则

> 本文件定义从 `参考/Kugua`（.NET 原项目）迁移功能模块时的取舍与忠实度要求。
> 迁移工作在本平台核心（能力注册表 / 知识库 / WebUI / MCP / Job）完成后再逐步进行。

## 一、总体原则

1. **只复刻"功能模块"**，不迁移原项目的整体架构、宿主形式与账户/登录态相关能力。
2. **忠实于 C# 实现**：算法与规则必须逐条对齐，**禁止"想当然地简化"**。
3. **可独立可用**：跨语言、跨进程的外部能力（如 ImageMagick / ffmpeg）应封装为本平台的独立功能模块，
   而不是散落在各处的临时调用。
4. **失效或依赖外部服务的模块**，先测试其当前可用性，再决定是否迁移；不确定时先询问，不盲目复刻。
5. 迁移顺序：**先核心平台，后功能模块**。核心未稳定前不铺开功能复刻。

## 二、明确不做

以下能力与原项目的账户/社交生态强绑定，不作为本平台功能：

- QQ 号获取、群成员反查、头像查询等需要 IM 适配器的能力；
- 积分 / 签到 / 转账 / 排行榜 / 红包等账户与虚拟经济系统；
- 其他依赖 QQ / Telegram 等外部平台登录态的玩法。

> 保留 Napcat/OneBot 桥接代码仅作为可选的 IM 入口，不投入深化。

## 三、忠实复刻要求（重点）

以下类型必须严格按 C# 原始实现迁移，不得改用"近似"或 AI 生成替代：

| 类别 | 要求 |
| --- | --- |
| 占卜（周易/筮草） | 完整复刻大衍筮法的分蓍、挂扐、归奇等每一步细节与随机过程 |
| 胡言乱语 / 垃圾文本生成器 | 严格按原项目的语法、句法与词库规则生成，不得简化或替换为模板拼接 |
| 数字论证 | 逆波兰搜索、字母序号/笔画数等算法完全一致 |
| 历法换算 | 公历/农历/回历/四柱/节气等换算规则完全一致 |
| 骰子 / 游戏结算 | 随机分布与结算规则一致 |
| 文本乱序 / 火星文 / 编码类 | 映射表与算法一致 |

> 判定标准：给定相同输入与随机种子，输出应可复现并符合原实现语义。

### 保真核对方法（已实践）

复刻算法不能只靠“看起来对”。可用 **.NET 实测参考项目依赖的库** 作为基准：

1. 参考项目编译产物在 `参考/Kugua/output/Debug/net10.0-windows10.0.19041.0/`，其中 `Prophecy.dll`
   等第三方库即 C# 侧的算法来源（如 `Prophecy.JDateTime` 提供农历/回历/儒略日/四柱/节气）。
2. 用 `dotnet` 新建控制台程序并 `<Reference Include="Prophecy"><HintPath>…</HintPath></Reference>`，
   直接调用或反射打印期望值（本机 `dotnet` 10.x 可直接引用该 net10.0 DLL）。
3. 与 TS 实现对比**批量样本**（建议 ≥40 例，含闰月/月界/闰年等边界），不一致即视为移植缺陷。

**已据此修正的移植缺陷**（详见 `更新日志.md`）：

| 位置 | 缺陷 | 修正 |
| --- | --- | --- |
| `lunar.ts` `儒略日` | 旧公式结果偏大 2～3 天 | 改用标准 Gregorian→JDN 并减 0.5（40 例全吻合） |
| `lunar.ts` `公历转回历` | 返回 30 年周期内序号（如 35）而非绝对回历年 1445；儒略日基准错误 | 改用表格算法返回绝对年（40 例 39 一致） |
| `lunar.ts` `公历转农历` | 闰月边界漏了 `--i`，闰月初一被报成 `leap+1` 月（2023-03-22 报“闰三月”，应为闰二月） | 补上 `--i`（1666 例逐日比对从 68 处不一致降至 18 处） |
| `infotool/bigutil.ts` `位数` | 用字符串长度代替 C# 的 `floor(Log10(n)+1)`，`10^3` 处多补 1 位 | 改用对数形式（`DivToString(355,113,4)` 由 `3.0141` → `3.141`） |

**已验证一致（未改动）**：四柱（`Prophecy.LunarFourPillars`，220 例抽样 0 不符）、干支/生肖/星期/节日/
星座/朝代、`Calculator` 表达式求值（含 `-2^2=4` 这类 C# 优先级行为）、`MathProof` 数字论证。

**精度与参考库缺陷**：

- （已解决）`节气日` 原为经典固定偏移表，对 `Prophecy.Jieqi` 在 2020-2029 抽样 220 个节气日中
  有 9 个相差 1 天（约 4.1%）→ 已改为 **天文算法**（Meeus 太阳视黄经 + 牛顿迭代，东八区 + ΔT 修正），
  对 Prophecy **660 个节气日（1902–2099 抽样）全部一致**（含 2045 小暑这类距午夜仅 51 秒的边界例）。
- **参考库自身缺陷（不复制）**：`Prophecy.JDateTime` 在 2023-12-13 ～ 2023-12-2x 区间返回错误的
  `LunarYear=2022`、月/日卡在 `11/1`、`LunarMonthReal=0`；本实现给出正确的 `2023/11/N`。
  另：Prophecy 每年仅标记 22 个节气日（自身遗漏 2 个），故基准集为 660 而非 720。

## 四、应迁移为独立模块的外部能力

原项目通过本地程序或库实现、且脱离 IM 仍独立有用的能力，迁移为本平台的独立功能模块：

- **图片处理**：原 .NET 的 `System.Drawing` / ImageMagick.NET 相关能力（编辑、网格、做旧、抠图、
  像素字、验证码、幻影坦克、拼接、GIF 处理、抖动等）迁移为独立图片模块；
  基础编辑优先使用轻依赖的本地实现，重型/ML 操作再调用外部程序。
- **音视频处理**：ffmpeg 相关的转码、剪辑、GIF 生成、抽帧、拼接等封装为独立模块。
- **文档 / 文本处理**：格式转换、索引、OCR 等。
- **算法工具**：计算器、编码换算、数字论证、历法等纯计算模块。

## 五、需先测可用性再决定的外部依赖

以下模块依赖外部服务或接口，原实现可能已失效。迁移前先单独测试可用性，再向项目所有者确认：

- Google 翻译 / Google 搜索 / 搜狗等网页抓取型接口；
- 各类在线 AI / 中转平台 API（LLM、图像生成、语音）；
- 点歌 / 新闻 / IP 归属等在线查询；
- 其他第三方在线 API。

处理方式：**能本地替代的优先本地化**（如本地翻译模型、本地 LLM）；
无法替代且已失效的，标记为"延后/不做"并记录原因。

## 六、AI 的定位

- AI 是**可选外部能力**，不是必需依赖；无 AI 时全部功能仍应可用。
- 已确认可用的 AI 能力，通过统一网关接入，供需要它的模块调用。
- 不允许用 AI 替代第第三节要求忠实复刻的确定性算法。
