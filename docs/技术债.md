# 技术债清单

> 本文件记录苦瓜工作室在开发过程中发现的、尚未偿还的技术债务。
> 每项标明「发现位置、现状、影响、建议方案、优先级」，按优先级排序逐步消化。
> 已偿还的债务移除或在行内标注 `[已还]`。

优先级约定：
- **P0**：会导致数据丢失 / 安全漏洞 / 静默错误，必须尽快处理
- **P1**：架构级不一致，拖慢后续开发或阻碍正确功能
- **P2**：可读性 / 可维护性 / 性能问题，不紧急但应计划处理

## mkg（知识图谱）模块

### [已还] 关系层双轨：`node_relations` 与 `resource_relations` 并存

- **发现位置**：`packages/mkg/src/db.ts`（两表都建了）、`packages/mkg/src/domains/resources.ts`（`addRelation`/`getRelations` 仍写 `resource_relations`）
- **现状（已修复）**：`addRelation`/`getRelations` 已迁移到 `node_relations`（节点维度），handler 参数改为 `fromNodeId`/`toNodeId`/`nodeId`，`getStats` 关联数改查 `node_relations`。旧 `resource_relations` 表保留（含幂等迁移逻辑），未来彻底清理时再删。
- **影响（已消除）**：节点维度关系可正常查询；`getStats` 关联数反映真实写入。
- **偿还方式**：提交 `关系层迁移`（addRelation 写 node_relations；getRelations 读 node_relations；handler 参数改 node 维度）。

### [P2] `nodes.meta` JSON 滥用：结构化字段塞黑盒 JSON

- **发现位置**：`packages/mkg/src/domains/materials.ts`（`kind/sourceUrl/imageUrl` 塞 meta）、`board.ts`（`columnId/color/sort` 塞 meta）
- **现状**：`nodes.meta` 是 `TEXT` 存 JSON，被用来存本应是结构化列的字段。不可查询、易损坏（手拼 JSON）、读写时都要 `JSON.parse/stringify`。
- **影响**：
  - 无法按 `sourceUrl`/`kind` 做 SQL 检索（未来 AI 检索素材来源需要）。
  - 素材/看板字段散落在 JSON 里，与强类型 `素材`/`卡片` 接口脱节。
- **建议方案**（分两阶段）：
  1. **接口收敛（先行）**：前端改走强类型接口 `mkg.material.get`/`mkg.card.get`，不再从 `listAllContent.meta` 手翻字段（这是当前反模式，见下方 P1 项）。
  2. **拆列（按需）**：当确实需要按 `kind/sourceUrl/imageUrl` 做 SQL 检索时，再把这些字段拆成 `nodes` 真实列（素材的「内容属性」优先拆；看板的 `columnId/color/sort` 属「展示态」，可暂缓）。数据尚未大量导入，迁移成本≈0。
- **优先级理由**：当前无查询诉求，不紧急；但接口收敛应先行（避免继续固化手翻 JSON 的模式）。

### [P1] 前端从 `listAllContent.meta` 手翻结构化字段（接口误用）

- **发现位置**：`packages/webui/src/renderer/parts/07e-explorer-materials.ts` 的 `打开素材编辑`——从 `item.meta` 手翻 `kind/sourceUrl/imageUrl`，而非调用已有的强类型 `mkg.material.get`。
- **现状**：后端 `mkg.material.get` 已返回强类型 `素材`（含 `kind/sourceUrl/imageUrl`），但前端绕过它，从统一列表的 `meta` 黑盒 JSON 里抠字段。
- **影响**：
  - 「界面前端与数据模型耦合」：字段一旦从 `meta` 移走或改名，前端就静默读到空值。
  - 违反「与界面解耦」目标——前端依赖的是 `meta` 的实现细节，而非稳定的公开接口。
- **建议方案**：前端双击打开编辑时改调 `mkg.material.get(id)` 拿强类型素材，再填对话框。多一次本地 IPC 往返，性能损失可忽略（本软件仅本地使用）。
- **优先级理由**：是「与界面解耦」的直接障碍，且是方案 B 的落地点。

### [已还] `mkg.data.read` 语义混乱：按 path 读 text_contents

- **发现位置**：`packages/modules/mkg/src/index.ts` 的 `mkg.data.read` handler
- **现状（已修复）**：`mkg.data.read` 支持 `nodeId` / `resourceId` / `path` 三种定位（优先级 nodeId > resourceId > path），新增 `mkg.readContentByNode(nodeId)` 按节点读索引文本。错误信息指明具体定位方式与失败原因。能力声明同步补充 `mkg.data.read`。

### [已还] `getStats` 的 `关联数` 依赖废弃表（随关系层迁移一并修复）

- **发现位置**：`packages/mkg/src/domains/files.ts` 的 `getStats`
- **现状（已修复）**：`关联数` 已改为查 `node_relations`（随关系层迁移完成）。

### [P2] `listAllContent` 全表载入 + 内存过滤 + N 次子查询

- **发现位置**：`packages/mkg/src/domains/nodes.ts` 的 `listAllContent`
- **现状**：`SELECT * FROM nodes` 全量载入，每行再 `获取节点内容`（N 次查询）+ `getNodeTags`（N 次）+ `获取标签路径`（N×M 次）+ `statSync`（外部文件）。数据量大时 O(N²) 级。
- **影响**：数据量上来后统一浏览/检索会慢；当前数据量小，不明显。
- **建议方案**：改为 SQL JOIN 一次取齐（节点 + 内容 + 标签），标签路径用内存缓存，`磁盘已变更` 的 `statSync` 按需（或批量 stat）。属性能优化，数据量大时再做。
