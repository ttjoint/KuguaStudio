# 技术债清单

> 本文件记录苦瓜工作室在开发过程中发现的、尚未偿还的技术债务。
> 每项标明「发现位置、现状、影响、建议方案、优先级」，按优先级排序逐步消化。
> 已偿还的债务移除或在行内标注 `[已还]`。

优先级约定：
- **P0**：会导致数据丢失 / 安全漏洞 / 静默错误，必须尽快处理
- **P1**：架构级不一致，拖慢后续开发或阻碍正确功能
- **P2**：可读性 / 可维护性 / 性能问题，不紧急但应计划处理

- **发现位置**：`packages/mkg/src/db.ts`（两表都建了）、`packages/mkg/src/domains/resources.ts`（`addRelation`/`getRelations` 仍写 `resource_relations`）

- **影响（已消除）**：节点维度关系可正常查询；`getStats` 关联数反映真实写入。
- **偿还方式**：提交 `关系层迁移`（addRelation 写 node_relations；getRelations 读 node_relations；handler 参数改 node 维度）。

### [已还] 测试假绿：`listAllContent` 分类过滤用错分类值

- **发现位置**：`packages/mkg/test/mkg.test.ts` 的「listAllContent 汇总各类内容并按分类筛选」
- **现状（已修复）**：测试用 `categories: ["note"]`，但 `内容分类` 的真实值是 `"点子"`（note 类型的分类名）。`["note"]` 匹配不到任何条目 → 过滤结果为空数组 → `.every()` 恒真 → 假绿。已改为 `categories: ["点子"]` 并新增「非空」断言（`仅笔记.length > 0`）。
- **教训**：对「过滤结果」做 `.every()` 断言前，必须先断言结果非空，否则空数组会让 `.every()` 恒真。
- **反向验证**：临时把 `获取内容分类` 的 note 返回值改错 → 非空断言红。

### [已还·素材部分] `nodes.meta` JSON 滥用：素材字段未拆真列

- **发现位置**：`packages/mkg/src/domains/materials.ts`（`kind/sourceUrl/imageUrl` 塞 meta）、`board.ts`（`columnId/color/sort` 塞 meta）
- **原现状**：`nodes.meta` 是 `TEXT` 存 JSON，被用来存本应是结构化列的字段。不可查询、易损坏、读写都要 `JSON.parse/stringify`。
- **影响**：无法按 `sourceUrl`/`kind` 做 SQL 检索（AI 检索素材来源需要）。
- **已做（素材部分）**：
  - `material_contents` 新增真列 `kind` / `source_url` / `image_url`（`确保素材表` 幂等 ALTER），并建 `idx_material_source_url` 索引。
  - **旧库自动回填**：`确保素材表` 一次性把 `nodes.meta` 里的字段搬进真列（仅真列仍为空时）；一次性守卫避免每次 CRUD 重复扫描。
  - **读写以真列为准**：`createMaterial` / `updateMaterial` 写真列（meta 仍同步，兼容旧版本程序）；`getMaterial` 真列优先、为空才回退 meta。
  - **新增检索**：`listMaterialsBySourceUrl` + handler `mkg.material.listBySourceUrl` + 能力声明（只读）——AI 现在能按来源 URL 查素材。
- **踩坑记录**：`SELECT ... WHERE source_url = ? ORDER BY node_id DESC` 在本机 better-sqlite3 + Node 24 上会走索引扫描并触发原生断言崩溃（`env != nullptr`）。改为 SQL 不带 ORDER BY、取回后内存排序。
- **仍未做（看板部分）**：`cards` 的 `columnId/color/sort` 属「展示态」而非「内容属性」，暂无 SQL 检索诉求，保留在 meta。若将来需要按列筛选卡片再拆。
- **回归护栏**：`mkg.test.ts` 新增「真列化：字段落真列，可按 sourceUrl 检索」。反向验证：去掉真列写入（只写 meta）→ 查询为空，测试红。

### [已还] `listAllContent` 全表载入 + 内存过滤 + N 次子查询

- **发现位置**：`packages/mkg/src/domains/nodes.ts` 的 `listAllContent`
- **原现状**：`SELECT * FROM nodes` 全量载入，每行再 `获取节点内容`（N 次查询）+ `getNodeTags`（N 次）+ `获取标签路径`（N×M×深度 次）+ `statSync`（外部文件，N 次系统调用）。总代价 O(N×M×深度)。
- **影响**：数据量上来后统一浏览/检索会慢；AI 的 `mkg.ai.search` 也走这条路，直接拖慢智能任务。
- **已做的优化**（本次）：
  1. **批量预加载**：新增 `批量加载标签索引`（一次 JOIN 取全部 node→tag + 全量标签表）、`批量加载正文索引`（5 张内容表各一次全查）、`批量加载资源索引`（resources 一次全查）；循环内只做 Map 命中。
  2. **标签路径改内存递归**：新增 `取标签路径从索引`，用预加载的标签表回溯，不再每级查库。
  3. **`statSync` 后置**：只对最终 `limit` 后的返回集做磁盘 mtime 检查，不再遍及全集。
- **实测**：2000 节点 / 500 标签（多级嵌套）场景，`listAllContent` 平均 13.2ms（未优化时同场景需数百 ms）。
- **回归护栏**：`mkg.test.ts` 新增「批量加载：tagPaths / 正文 / 资源字段与逐条查询等价」——用逐条接口 `getNodeTags` / `获取标签路径` 对账，防批量实现偏移；另加「磁盘已变更只对返回集检查」。反向验证：破坏路径回溯 → 测试红。
- **注**：仍是全表载入 + 内存过滤（未改 SQL 层）。数据量再上一个量级时应加 `LIMIT` 下推与索引，但已不再是 O(N²)。

## 工具链踩坑

### 行尾符噪音：编辑工具把整个文件重写为 LF

- **现象**：改了 `packages/main/src/index.ts` 约 15 行，提交后 `git show --stat` 显示 **3551 行变更**。
- **原因**：仓库配置 `core.autocrlf=true`（检出转 CRLF、提交转 LF），而某些编辑工具会以 LF 重写整个文件；
  一旦文件内混用行尾，git 就把它当作「全文件重写」。
- **真实改动**：`git diff --ignore-all-space HEAD~1 HEAD -- 文件` 只显示 15 行（15 增 2 删）。
- **处理**：把文件统一回 CRLF（`\r\n`）后，工作区与 HEAD 一致，后续 diff 不再被污染。
- **预防**：大文件改少量行后，先跑 `git diff --stat` 确认变更行数合理；
  异常时用 `git diff --ignore-all-space` 看真实改动，再统一行尾。

### 标签无「移动」能力（P2）

- **现状**：标签只能新建/删除，不能改父节点（无 `mkg.tag.move`）。
- **影响**：一旦标签被挂错位置（如历史上 `createTag` 的 ON CONFLICT bug 造成的错乱），
  用户只能删掉重建，已打在该标签上的内容会丢关联。
- **建议**：补 `mkg.tag.move({ tagId, newParentId })`，前端标签树加拖拽。

### 已修复：createTag 同名标签被「搬家」

- **bug**：`tags.name` 全局 UNIQUE + `ON CONFLICT(name) DO UPDATE SET parent_id = excluded.parent_id`，
  导致重新创建已存在的同名标签时，会把它从原父节点**搬走**。
- **现象**：详情栏连续输入两个标签，后一个看起来像被挂到前一个下面（树结构错乱）。
- **修复**：同名时返回已有标签（位置不变），只允许更新描述。
- **回归**：`packages/mkg/test/tags-create-stability.test.ts` 5 用例。
